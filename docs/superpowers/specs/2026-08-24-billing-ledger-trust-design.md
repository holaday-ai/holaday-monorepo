# 账单流水可信化设计

## 1. 背景与问题

当前 `/billing` 同一列表混排 `pending`、`failed`、`completed` 与 `refunded`，标题是“交易记录”，但正文实际展示的是“最近 20 笔支付尝试”。当用户重复打开结账页时，未完成尝试会挤占固定 20 条窗口，较早的真实付款可能不可见。

这会制造两类信任问题：

1. 用户无法快速回答“我实际付过哪些钱”；失败或放弃的结账看起来和真实付款同等重要。
2. 固定窗口不是完整流水。即使历史付款仍在数据库中，界面也可能让用户误以为记录丢失。

本轮采用已确认的方案乙：把“已发生的资金结果”作为主流水，把“未完成支付”降为按需查看的辅助记录，并为两部分提供相互独立的安全分页。

## 2. 目标与成功标准

### 2.1 目标

- 用户进入页面后优先看到当前订阅和真实付款结果，不被结账尝试干扰。
- 已支付或已退款记录不会因新增失败、取消或待确认订单而被挤出首屏或永远无法访问。
- 用户可复制订单号，并能从具体订单发起付款凭证或发票咨询。
- 保持账户隔离、最小数据暴露和现有支付结算语义不变。
- 桌面端信息清晰，390px 移动端不产生横向滚动或过长的混排列表。

### 2.2 可验收结果

1. “付款记录”只包含 `completed` 与 `refunded`。
2. “未完成支付”只包含 `pending` 与 `failed`，默认折叠，第一次展开时才请求数据。
3. 两个分组分别分页；新增未完成订单不改变付款记录分页结果。
4. 每个付款记录可复制 HOLA DAY 订单号；“申请凭证/发票”打开已预填该订单号与用户待补信息的支持邮件。
5. 任一查询失败只影响对应分组，不隐藏当前订阅，也不清空另一分组已加载的数据。
6. 用户甲永远不能通过输入、游标或订单号看到用户乙的记录。

## 3. 非目标

- 不改变支付创建、捕获、回调、退款、套餐发放或幂等结算逻辑。
- 不修改 `payments` 表、支付供应商配置、生产环境变量或历史数据。
- 不在本轮建设正式电子发票开具、PDF 凭证下载、财务后台或自动邮件发送系统。
- 不把 `pending` 自动改写为 `failed`；陈旧待确认仅在展示层标为“未完成”。
- 不向前端返回支付网关订单号、捕获号、付款人邮箱、原始回调、`metadata`、用户标识或数据库主键。

## 4. 信息架构

页面继续保持“当前订阅 → 支付方式 → 付款记录”的主顺序，在付款记录后增加低优先级的“未完成支付”。

### 4.1 付款记录（主区）

- 标题：`付款记录`
- 说明：`已确认到账或已退款的记录`
- 数据：`completed`、`refunded`
- 默认首屏：10 条，按 `createdAt DESC, externalId DESC` 稳定排序
- 行内容：产品、支付方式、付款/退款状态、金额、付款确认时间、订单号、操作；当前数据没有退款发生时间，已退款行不得把付款确认时间误标成退款时间
- 行操作：`复制订单号`、`申请凭证/发票`
- 分页方式：底部“加载更多”；加载期间保留已有行
- 空状态：`暂无付款记录`，补充说明“完成订阅或购买加量包后会显示在这里”

### 4.2 未完成支付（辅助区）

- 默认是一个折叠条，不在页面初始化时请求列表。
- 文案：`查看未完成支付`；辅助说明：`包括取消、失败或仍待确认的结账记录，不代表已扣款`
- 用户展开后请求第一页，每页 10 条，并提供独立“加载更多”。
- `pending` 在创建后 30 分钟内显示“待确认”；超过 30 分钟显示“未完成”。
- `failed` 显示“支付失败”；两者都明确写“未确认扣款”。
- 不提供申请凭证/发票操作；可复制订单号，便于用户就异常支付联系支持。

## 5. API 与数据契约

新增受保护查询 `payment.ledger`，不直接破坏现有 `payment.history`：

```ts
type PaymentLedgerInput = {
  section: 'settled' | 'unfinished';
  cursor?: {
    createdAt: string; // ISO 8601
    orderId: string;   // 上一页最后一项的公开订单号
  };
  limit?: number; // 默认 10，最小 1，最大 20
};

type PaymentLedgerPage = {
  items: Array<{
    orderId: string;
    provider: string;
    kind: string;
    plan: string;
    amountCents: number;
    currency: string;
    status: 'pending' | 'completed' | 'failed' | 'refunded';
    createdAt: string;
    completedAt: string | null;
  }>;
  nextCursor: { createdAt: string; orderId: string } | null;
};
```

### 5.1 查询规则

- `settled` 映射到 `status IN ('completed', 'refunded')`。
- `unfinished` 映射到 `status IN ('pending', 'failed')`。
- 所有查询必须同时包含 `payments.userExternalId = ctx.userId`；游标条件不能替代或放宽租户条件。
- 排序固定为 `createdAt DESC, externalId DESC`。下一页条件为：
  - `createdAt < cursor.createdAt`，或
  - `createdAt = cursor.createdAt AND externalId < cursor.orderId`。
- 数据库取 `limit + 1` 条判断是否还有下一页，只返回前 `limit` 条。
- `nextCursor` 只来自本次返回的最后一条；非法日期、非法订单号、越界 limit 或未知 section 由 Zod 在查询前拒绝。
- 前端仍把所有网络返回视为不可信输入，按页面状态模型做字段归一化；单条非法记录被丢弃，不让整页崩溃。

### 5.2 兼容策略

- 本轮新增 `payment.ledger` 并迁移 `BillingPage`；保留 `payment.history`，避免对潜在旧客户端产生破坏。
- 是否删除 `payment.history` 留给后续独立清理，不与本轮信任修复捆绑。
- 不新增数据库索引。现有 `ix_payments_user_status` 可先支持按用户和状态过滤；若生产可观测数据证明分页查询变慢，再单独评估复合索引迁移。

## 6. 交互与视觉设计

### 6.1 视觉层级

- 延续现有 HOLA DAY 账单页的白底、低噪声边框和轻阴影，不引入高饱和营销卡片。
- 付款记录是完整 Section；未完成支付使用更轻的折叠容器，避免与真实付款争夺注意力。
- 金额使用等宽数字并保持最强的行内信息权重；状态、订单号和操作次一级。
- `已支付` 使用克制的绿色，`已退款` 使用中性灰，`待确认/支付失败` 使用琥珀色，不使用红色制造“已扣款”误解。

### 6.2 桌面端

- 付款行采用两栏：左侧产品、渠道、时间、订单号；右侧金额、状态与操作。
- “复制订单号”与“申请凭证/发票”是文字按钮，不扩大为主按钮。
- 加载更多位于列表底部，按钮旁可显示“正在加载”；失败时原地出现“重试”，已加载内容不消失。

### 6.3 390px 移动端

- 每条记录改为纵向卡片式行：首行产品 + 状态，第二行金额 + 时间，订单号与操作单独换行。
- 订单号允许断行但复制按钮保持可点击；操作区不挤压金额。
- 所有按钮和折叠触发器点击区域至少 44×44px。
- 页面不得产生横向滚动；长订单号、异常产品名和本地化金额均需覆盖测试。

### 6.4 状态与反馈

- 首次加载：付款记录显示 3 条骨架；未完成支付保持折叠且不显示骨架。
- 空状态、首次加载错误、加载更多错误分别处理。
- 复制成功显示短暂的行内反馈 `已复制`；失败显示 `复制失败，请手动选择订单号`。
- 折叠按钮使用 `aria-expanded` 与 `aria-controls`；加载、错误和复制反馈使用合适的 `aria-live="polite"`。
- 键盘焦点可见；图标若无文字必须同时有 `aria-label` 和原生 `title`。

## 7. 凭证与发票咨询

“申请凭证/发票”不是自动开票。它打开支持邮箱草稿：

- 主题：`HOLA DAY 付款凭证与发票申请 · {orderId}`
- 正文预填：订单号、产品、金额、支付时间，以及由用户补充的发票抬头、税号、接收邮箱。
- 不在 URL 或正文中放置内部用户 ID、网关订单号、捕获号或付款人邮箱。
- 用户点击只创建本地邮件草稿；是否发送仍由用户确认，不产生静默外部副作用。

## 8. 隐私与安全边界

- 查询必须是 `protectedProcedure`，身份只来自服务端会话 `ctx.userId`。
- 客户端不能传 `userId`；服务端也不接受用于切换账户的字段。
- 返回白名单字段，明确排除 `metadata`、`providerOrderId`、`providerCaptureId`、`userExternalId`、数据库 `id` 与付款人资料。
- 游标即使来自其他账户，也只能在当前账户过滤后的结果集上定位，不可形成跨账户探针。
- 错误文案不区分“游标属于其他账户”和“该页不存在”，不泄露记录存在性。
- 复制和邮件模板只使用已返回的公开订单号及展示字段。

## 9. 错误处理与并发语义

- 页面初始化并行加载当前订阅和第一页付款记录；任一失败不阻断另一部分。
- 未完成支付仅在第一次展开时加载，之后折叠/展开复用已加载结果。
- 每个分组维护独立的 `loading`、`loadingMore`、`error`、`nextCursor` 与请求序号，防止慢响应覆盖新响应。
- 连续点击“加载更多”时只允许一个在途请求；相同 `orderId` 在前端合并时去重。
- 支付回跳确认成功后刷新当前订阅和付款记录第一页；不自动展开未完成支付。
- 如果支付状态在分页期间变化，可能从未完成组移动到付款组；页面刷新后以服务端当前状态为准，不在客户端伪造结算结果。

## 10. 测试计划

### 10.1 服务端

- `settled` 只返回 `completed/refunded`，`unfinished` 只返回 `pending/failed`。
- 用户隔离：混合夹具中只返回当前 `ctx.userId` 的记录。
- 组合游标在相同毫秒创建的多条记录上无重复、无遗漏。
- 两组分页互不影响；新增失败订单不改变 settled 第一页。
- limit 默认值、上下界、非法 section、非法日期和非法订单号均按契约处理。
- 返回对象不包含用户、网关和 metadata 字段。
- 现有创建、捕获、回调与幂等测试保持通过。

### 10.2 前端状态模型

- 不可信响应归一化、非法条目丢弃、nextCursor 校验与分页去重。
- 分组映射、陈旧 pending 文案、金额/时间/产品/渠道格式化。
- 订单复制反馈和带订单号的支持邮件模板。
- 首次错误与加载更多错误不会清空已加载记录。

### 10.3 页面与可访问性

- 桌面端与 390px：有记录、无记录、长订单号、两组多页、加载和错误状态。
- 未展开时不请求 unfinished；展开后只首次请求，加载更多使用独立游标。
- 折叠触发器、复制、申请和加载更多均可用键盘操作，焦点可见。
- 图标按钮满足 `aria-label`、`title`，状态反馈可被辅助技术感知。

## 11. 上线与验证

1. 合并前运行支付路由测试、账单状态测试、页面测试、类型检查、触及文件 lint 与 `git diff --check`。
2. 本地浏览器验证桌面和 390px，保存付款/未完成分组、展开、复制和分页证据。
3. 部署 application，不部署支付供应商或数据库服务。
4. 生产只读验证：健康检查 200、已登录账单页可用、真实成功记录只在付款记录、未完成尝试只在折叠区、移动端无横向滚动。
5. 检查部署后支付路由错误日志，不读取或输出付款人资料和原始支付 metadata。

## 12. 回滚

- 若新查询或页面出现阻断问题，回滚 application 到上一生产版本即可；本轮无数据库迁移或历史数据写入。
- 保留的 `payment.history` 使回滚不依赖服务端契约逆向迁移。
- 回滚不修改任何订单状态，不重复捕获或退款。

## 13. 后续独立候选

- 正式电子发票/凭证生成、下载与申请状态跟踪。
- 财务支持后台与退款/争议处理流程。
- 生产查询数据证明必要后，再评估 `(user_external_id, status, created_at, external_id)` 复合索引。
- 旧客户端确认退出后，清理 `payment.history`。
