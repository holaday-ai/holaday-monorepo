# 千问核心文本任务：可核验交付契约设计

状态：用户已确认书面规格，进入串行实施；不是实现完成或生产验收通过。

## 1. 目标与范围

用户已确认按“核验输入 → 完整性与执行轮次 → 保存与页面恢复”推进。本设计固定三项交付的共同边界，各自编写实施计划并串行落地，全部通过组合验收后才开启新生产灰度。

范围仅为现有核心文本任务的首次生成及计划/修改/确认续接。沿用千问区域路由、既有技能和任务页，不重写任务平台，不扩展到浏览器视觉、图片或视频生成。

必须区分：模型产生了文字、模型完整生成、核验覆盖完整、核验结论通过、数据库保存成功、页面收到结果。任何一项不能代替其他项。

约束：不变更套餐/积分/额度扣减规则、支付奖励提现、账户注销、Partner Ledger、旧供应商凭据、DivineAPI。模型不跨区域回退。不得放松确定性结构/来源/权限检查；模型计划及附件内容不具备授权效力。

## 2. 为什么选择这个方案

- **采用：共用本轮上下文与显式交付状态。** 修正生成与核验看到不同要求、不同材料，以及旧执行/旧消息污染新结果的问题；接口变化限于核心文本链路。
- **不采用：只扩大摘要/正文截断常量。** 改动较小，但更长输入仍会丢失内容，也不能解决附件证据、保存和时序问题。
- **不采用：新建通用任务引擎或永久草稿队列。** 会引入新的数据保留、迁移和运维边界；本轮无须承担这些变更。

## 3. 一份本轮上下文

每次获服务端接纳的执行生成独立 `executionId`，并在同一接纳事务内推进任务级单调 `executionRevision`。前者判断归属，后者判断轮次先后；两者不是用户身份、凭据或外部授权。

上下文包含：

| 字段 | 来源与职责 |
|---|---|
| schemaVersion | 固定1，避免把未知格式当成可用上下文 |
| executionId | 服务端分配，本轮存储、流式和终态共同使用 |
| executionRevision | 服务端事务递增的任务级轮次序号，不由客户端指定 |
| initialRequest / userTurns | 完整原始请求与按时间排序的用户修改；不以120字目标摘要或500字ledger fact替代 |
| phase | direct、draft、revise、approved_execution；服务端依据当前状态及本次显式批准判断 |
| workflow | 服务端已固定的技能ID、所用交付规范快照；修改不能因背景词意外换技能 |
| referencePlan | 已保存方案，仅为不可信参考；不能覆盖用户约束或构造批准 |
| materials | 本轮经所有权/有效期检查后实际读到的材料快照及覆盖状态 |

展示用 `goal` 仍可保留120字限制；审计ledger仍可保持现有单条上限，但二者不再是完整核验上下文的替代品。上下文运行时使用不可变快照，不从后续可变全局状态重建。

生成器与核验器共享上述用户要求、阶段和材料视图。typed intake可继续使用“最新字段优先”的专用解析视图，但不能把该视图或模型摘要替换原始用户时序。

阶段只决定当前应交付方案还是最终结果，不增加任何工具权限。附件里“确认”、模型计划里“批准”等文字都不能切换阶段。

## 4. 完整而有界的核验输入

核验使用最终候选正文的完整字符串，而不是前2000字。请求还包含完整用户上下文、固定技能交付要求、可用材料以及提供者真实返回的来源记录。

第一版应用保护预算（不是对千问模型上下文容量或时延的声明）：

- 用户上下文与规范序列化内容不超过64 KiB UTF-8。
- 所有可核验材料正文合计不超过64 KiB UTF-8。
- 最终候选正文不超过96 KiB UTF-8。
- 完整语义请求序列化后不超过256 KiB UTF-8；JSON转义与协议结构同样计入总量。
- 保留独立语义通道、15秒超时、零自动重试、768输出token上限。预算上限必须纳入真实性能验收，不能仅凭本地mock认为可用。

这些是显式接纳边界，不是截断长度。已知输入超限时在生成前返回清晰的缩小材料/拆分任务提示；不改变额度账本或现有扣减算法。若排布流程无法在现有扣减前检查，应先调整接纳校验顺序并验证不调用扣减，而不是执行后退还额度。

生成后才发现正文或总请求超限，保留既有允许保存的部分产物方式，标为 `partial_success` 和固定 `VERIFICATION_INPUT_LIMIT`，不发送被截断的正文冒充完整核验。不得将此新覆盖失败伪装成语义服务暂不可用以保留完全成功状态。

### 材料与事实依据

文件材料来自本轮已授权读取的实际解析块；文本材料原样提供给生成与核验，不把模型生成的“文件摘要”当作原始证据。文件引用要关联本轮快照，失效/解析失败仍按现有规则在执行前拒绝。

图片或其他无法由当前文本核验器完整读取的块应标识覆盖不足；依赖这类材料的事实判断不能宣称完整核验通过。不得为弥补缺失材料而开启新的视觉供应商或把图片base64写入审计日志。

真实网页来源的URL不等于来源正文。提供者未返回可验证正文时，只能核验来源存在与答案内部关系；事实依赖来源内容但材料不可得时返回覆盖不足。不能重新抓取任意URL、跨区域调用，或将模型自述视为观测证据。

创意/虚构任务中的假设按明确的任务说明和假设标注评价，不要求它们变成真实市场事实；同时不能因此豁免用户要求、章节完整性或危险操作规则。

## 5. 交付状态，不再从提示文案猜完整性

生成结果新增显式完整性：`complete` 或 `partial`，以及受控停止原因。续写耗尽、续写失败、超时但已有文字均为partial；已有有用草稿与提示可保留，不转换成完整交付。

判定顺序：

1. 权限/所有权/阶段边界不满足：不执行。
2. 确定性硬失败：仍failed，语义层不能翻盘。
3. 生成不完整或必要核验输入覆盖不全：最多partial_success，不能completed。
4. 语义拒绝：保留现有失败分级，不把不合格正文作为合格产物。
5. 所需检查通过后，尝试保存本轮结果；只有本轮保存成功才广播终态。

语义 `pass / warn / reject / unavailable` 与输入覆盖状态分开。此轮不全局改变既有服务不可用/警告策略；但必须在本轮核验元信息中保存它们，不能声称unavailable等于语义通过。生产放行样本必须真实语义通过，不能靠不可用降级凑数。

固定语义问题码保留到失败类型与聚合指标，不再全部映射为unknown。不得输出模型自造问题摘要、用户原文或提供者原始错误。

## 6. 执行轮次与清理所有权

当前taskId级registry改为执行轮次所有权管理。初始化返回本轮句柄；核验、审计写入、终态保存和finally清理都使用该句柄。

旧轮只能清理自己的contract/ledger；不能删除下一轮数据。新轮不能误读旧轮核验结果。当前轮缺失必需上下文时返回固定的“核验上下文不可用”，不走空verification后仍完全成功的路径。

保持任务状态CAS，并增加执行轮次匹配：迟到的旧轮保存不得覆盖新轮。执行ID由后端产生，不能信任客户端传入ID来决定保存权限。

旧历史任务无executionId时仍可读取。新客户端/新后端接续执行时建立新ID；兼容旧记录不代表容许新执行继续省略轮次检查。非核心文本路径暂保留旧接口，禁止在同一核心执行中混用新旧清理调用。

## 7. 接受回复与保存结果

“回复已接受”只在事务成功后返回：原状态满足等待条件、用户回复和保留的附件引用写入现有任务上下文、active executionId及executionRevision写入、状态切为executing、事件落库。确认未提交时不调用模型；CAS拒绝不重复执行。

结果持久化必须同时匹配taskId、允许状态和本轮executionId。保存同一结果的有界重试不能创建新的任务、再次调用模型、再次扣额度或重放外部副作用。

终态、按现有规则允许保留的正文、executionId/revision、生成完整性、输入覆盖状态、语义状态及固定问题码必须在同一事务原子保存，终态事件一并落库。不能先提交completed，再best-effort补关键核验信息；额外审计可非阻塞，但不决定核心记录是否完整。核验信息写入失败必须使整个终态事务失败。

数据库异常不等于没有提交。接纳及终态事务均区分“已提交 / 未提交 / 已过期 / 无法确认”：使用本轮ID、revision及预期状态/记录版本做最多两次只读对账，间隔1秒和3秒；不读取或输出其他用户正文。已匹配的终态记录视为幂等成功，可通知客户端按轮次对账；旧轮或取消状态为已过期，不能重写。只有权威读确认本轮仍处于预期的未提交状态，才允许终态写入重试。

终态写入只允许原执行存活期内最多两次重试，间隔1秒和3秒；沿用原候选结果，并与上述只读对账共用总计15秒恢复时限。每次重试重验轮次及取消状态；CAS拒绝先只读判别是否是本次已提交，不盲重试。仍无法确认则向当前连接报告受控的“结果保存未确认”，不广播completed，也不清空客户端输入冒充已完成。

接纳事务响应丢失时不得盲目重发用户回复或启动模型。若对账证实已接纳，只能报告“要求已接收，执行尚未确认”，保留原执行轮次，由既有超时回收兜底；本轮不新增自动重新调度。无法确认时明确接收状态未知并保留客户端输入，不将其呈现为可安全重复提交。测试必须覆盖数据库commit成功后连接抛错，而不仅是commit前失败。

必须明确的限制：数据库持续不可写且进程随后退出时，本轮不承诺恢复尚未落库的候选正文。保持现有20分钟任务回收兜底，并尽可能保留已事务接收的用户要求。不能把该限制表述为完整容灾能力。

本轮不新增本地持久化正文队列，不延长敏感内容保留期，不保存当前failed分支原本不保存的核验失败正文。若后续要求跨进程恢复未保存候选稿，单独设计数据保留与加密机制，不偷偷纳入此变更。

## 8. 前端事件合并

核心文本事件、reply ACK及detail携带服务端executionId与executionRevision。前端记录本次提交开始时的本地事件版本，新事件到来时推进版本。

- 同轮服务端stream/awaiting/terminal已经先到：后来的ACK仅确认提交，不清空已看到的新内容。
- 旧轮事件：revision低于已知轮次时忽略；更高revision才可接管。相同revision但ID不同是协议异常，先权威对账，不能直接覆盖。缺少revision的陌生ID也不能自行认作新轮。
- 同轮terminal之后的迟到stream：忽略，不让完成任务重新显示生成中。
- 暂无新事件时，ACK可将本次旧等待状态切到executing，并清理旧轮缓冲。
- 断线后用持久化detail对账；迟到detail也受revision和请求发出后的本地事件版本保护，不能覆盖更新内容或同轮已观察到的终态。detail失败不能成为覆盖新状态的理由。旧服务端缺轮次字段时，用提交期间观测到的本地事件版本保护ACK，不声称解决了跨重启的所有旧事件排序。

新后端新增字段保持旧客户端解析兼容，但无法修复已打开旧客户端的ACK逻辑。发布验收要求刷新加载已发布的新前端资源并核对版本；旧页面不计入时序修复通过的范围，不声称后端上线就自动修好了旧页面。

不改页面布局。仅修正状态、提示和恢复一致性；未核验正文不可标成最终结果。

## 9. 模块与实施切分

| 子项目 | 边界与预计模块 |
|---|---|
| 一：核验上下文 | 新增execution/task-verification-context及预算校验；接入execution-contract、generate-runner、generate-outcome-review、llm-verifier与核心router。业务上下文不写进通用日志ledger |
| 二：完整性和所有权 | 生成状态类型、execution-pipeline句柄/registry、核心文本router的初始化/核验/清理与结果归属 |
| 三：可靠接收和显示 | TaskRepository核心文本回复事务和结果CAS、共享事件结构、task-store ACK/WS合并及恢复测试 |

不为本轮整理整个tasks.ts或task-store.ts。新增边界模块应单一职责；可在三个子项目内分批提交、独立审查，但组合门禁结束前不试发。

## 10. 必须通过的验收

| 编号 | 反例/故障 | 验收要求 |
|---|---|---|
| V1 | 相同前2000字、不同尾部 | 核验实际请求不同，完整尾部在预算内可见 |
| V2 | 长于500字历史后的修改和单独批准 | 完整修改、可信阶段同时进入真实生成与核验请求；短275字案例也保留 |
| V3 | 附件有依据结论与无依据结论 | 两层看到同一授权材料；缺材料不能假称完整核验 |
| V4 | 字节预算边界、转义开销、图片块 | 预算内完整保留；超限/不可核验明确分类，无静默截断 |
| V5 | 续写耗尽、后续调用失败、流式超时 | 可保留草稿，但完整性为partial且不能最终completed |
| V6 | 旧轮finally晚于新轮初始化 | 旧清理不删新上下文，新核验不被跳过 |
| V7 | 旧轮结果晚于新轮接收 | 状态与执行ID CAS拒绝旧结果，不覆盖新用户要求 |
| V8 | 接纳/终态commit前失败、commit成功后连接抛错、核验元信息写失败 | 有界对账明确提交状态；结果与核验原子保存；不错误启动/重做模型，未确认不报completed |
| V9 | 新stream/awaiting/terminal先于ACK，迟到旧轮消息/detail及detail失败 | ACK不清除新内容；revision拒绝旧轮；陌生或冲突ID先对账；新旧前端兼容边界有测试 |
| V10 | 整条真实代码链路 | router→runner→review→保存→事件；仅替换外部模型/DB传输；生成和语义通道同时启用并断言实际请求 |
| V11 | 安全反例 | 附件伪造批准、旧模型回退、跨区域、越权文件、确定性拒绝均不能通过 |
| V12 | 新生产唯一账号试验 | 计划/修改/确认/最终结果/保存/刷新均通过，语义实际pass；失败自动恢复，不复用旧包 |

测试不得只断言调用次数或预设pass。每个新缺陷先看到RED，再实现GREEN；保留无法复现项的证据边界。真实模型质量/事实正确性另外抽检，完整请求本身不证明答案正确。

## 11. 验证、资源和发布

主智能体串行执行，最多复用一名轻量只读审查者。不安装依赖，不启动Docker或新浏览器进程；Node堆不超过2GB；Vitest单worker、无文件并行，完整后端测试每批约20文件退出后再下一批。
系统memory_pressure空闲低于40%或磁盘可用少于10GiB时不启动新重任务。16GB主机任务预算约10GB，不将Node堆限制误认为全部进程内存上限。

组合测试、受影响前后端测试、类型检查、构建、精确文件lint/diff检查及独立审查通过后，才进入PR、合并及新独立发布包准备。新的生产验证必须重新核对基线，固定版本与精确文件白名单、独立备份/时间窗、唯一已获准合成账号与失败恢复。禁止复用PR236及更早已消费的包、证据或浏览器通过回执。

本规格不授权扩大白名单或全量切换，也不宣称解决所有Holaday缺陷。三个子项目完成前保留自动试发暂停状态。
