# 文件库旧文件名信任修复设计

**日期：** 2026-08-22
**范围：** `/files` 文件库列表与搜索
**优先级：** P0 数据展示可信度兼容修复

## 问题

生产文件库中仍有上传修复上线前创建的记录，其 UTF-8 文件名曾被当作 Latin-1 保存。例如 `周报模板.xlsx` 以 `å¨æ¥æ¨¡æ¿.xlsx` 留在数据库。更老的数据还可能把乱码中的 U+00A0 归一化为空格，例如 `凌乱素材.txt` 变成 `åä¹±ç´ æ.txt`。当前列表直接返回原值，搜索也只匹配原始值，导致用户看到乱码，并且无法用本来认识的中文文件名找到文件。

新上传链路已经通过 `decodeUploadFilename` 修复，因此本次不修改上传、存储对象、数据库结构或历史数据。

## 目标

- 文件列表对已知 UTF-8/Latin-1 误解码的旧文件名进行只读显示修复。
- 用户使用正确中文查询时，同时兼容匹配数据库中的旧乱码值。
- 已正确的 Unicode、ASCII 和真实 Latin-1 文件名保持不变。
- 不回写数据库，不重命名存储对象，不改变文件 ID、下载或删除行为。

## 方案

### 返回值规范化

文件库路由复用上传服务现有的 `decodeUploadFilename(filename)`。该函数优先执行无损 Latin-1 到 UTF-8 解码；若失败且原名含不可能出现在正常文件名中的 C1 控制字节，只在 UTF-8 正等待续字节的位置把普通空格恢复为 `0xA0` 后重试。其他空格、真实 Latin-1 和已正确 Unicode 保持原样。

### 搜索兼容

将用户查询规范化为最多三个数据库匹配词：

1. 用户输入的原始查询；
2. 将查询的 UTF-8 字节按 Latin-1 表示所得的旧存储候选；
3. 若候选含 U+00A0，再加入其空格归一化变体。

候选去重后以 OR 连接。这样 `周报模板` 能匹配 `周报模板.xlsx` 和 `å¨æ¥æ¨¡æ¿.xlsx`，`凌乱素材` 能匹配空格归一化的旧值，ASCII 查询不会产生重复条件。

## 安全与边界

- 查询仍限制为 100 字符，并使用 Drizzle 参数化 SQL 条件。
- 只处理文件名元数据；不读取文件内容。
- 不执行数据迁移或生产写入。
- 不把通知开关无障碍命名、AI 记忆长列表重排混入本修复；二者作为独立后续项。
