# DivineAPI 真实内容自动升级提速设计

## 背景与根因

今日能量当前采用“8 秒前台预算 + 服务端后台完成 + 前端静默复查”的降级策略。首次查询超过 8 秒时，页面先展示可用的 Holaday 本地提示，DivineAPI 请求继续在服务端运行。

现有前端把第一次静默复查固定在收到本地提示 18 秒后。按生产 Translator 常见 21–25 秒响应计算，时间线为：

1. `0s`：页面发起真实内容查询；
2. `8s`：前台预算耗尽，页面展示本地提示；
3. `21–25s`：DivineAPI 通常已经完成并写入缓存；
4. `26s`：前端第一次静默复查，页面才切换为真实内容。

因此现象不是刷新机制失效，而是前端主动空等约 18 秒；用户在这段时间内无法判断页面是否还会自动更新，容易误以为必须手动刷新。

## 目标

- 首次 8 秒拿不到 DivineAPI 时，继续立即展示本地内容，不能恢复长骨架屏。
- 本地内容出现后立即进入静默等待，不再额外空等 18 秒。
- DivineAPI 完成后尽快原位替换内容，不要求用户点击刷新。
- 清晰但克制地提示“真实内容正在更新并会自动替换”。
- 保持服务端同键单飞、35 秒供应商硬超时和缓存契约不变。
- 不修改 Translator、OpenAI API Key、模型、套餐和接口权限。

## 已确认方案：静默长轮询 + 动态状态

### 前端复查节奏

当可见周期返回 `source: local-fallback` 且 `providerRefreshPending: true` 时，前端执行最多三次静默复查：

1. 收到本地提示后在下一个事件循环立即复查；
2. 若仍在后台处理中，1 秒后再复查一次；
3. 若仍未完成，再等待 1 秒后做最后一次复查。

前端对应的延迟序列固定为 `[0, 1_000, 1_000]` 毫秒，首项表示立即开始第一次静默查询，后两项是两次有界续查。结合每次服务端最多 8 秒的等待预算，这三次查询可以连续覆盖进入页面后约第 8–34 秒的供应商处理窗口。

每次 tRPC 查询都复用服务端现有的 8 秒前台等待预算。由于服务端按相同缓存键共享 in-flight promise，这些查询类似有上限的长轮询：它们不会创建第二个 DivineAPI 请求，而是等待同一个后台任务完成。生产常见 21–25 秒响应会在第二次或第三次静默查询期间直接返回，页面随即升级。

三次静默复查全部返回 pending、请求失败，或服务端最终普通降级时，前端停止自动复查并保留当前本地内容；刷新按钮继续可用。

### 页面状态表达

可见周期满足 `local-fallback + providerRefreshPending` 时：

- 星座专刊来源标签显示“真实星座内容更新中，将自动替换”；
- 标签使用现有马卡龙色系，并增加一个轻量呼吸圆点；
- 星座深度补给中的本地提示文案同步改为相同含义；
- 状态使用 `aria-live="polite"`，不打断用户当前操作；
- `prefers-reduced-motion: reduce` 下禁用呼吸动画。

如果服务端返回普通本地降级且 `providerRefreshPending: false`，继续显示“Holaday 本地提示”，不暗示一定会自动替换。

真实 DivineAPI 内容到达后：

- 原位更新标题、摘要、维度、幸运色和来源标签；
- 清除 pending 状态和本地提示；
- 不重新显示骨架屏，不转动手动刷新按钮，不移动页面滚动位置。

## 生命周期与竞态保护

沿用现有每周期 request id、range key 和 profile 身份守卫，并保留以下约束：

- 只复查当前可见周期；不预热周榜或十二星座数据；
- 用户切换周期时取消旧周期计时器并使旧响应失效；
- 用户切换月度范围、修改星座资料或手动刷新时，取消旧链路并重新计数；
- 组件卸载时清除全部计时器；
- 迟到响应不得覆盖新的资料、周期或范围；
- 静默查询不把 `loading` 改回 `true`。

## 服务端与成本边界

本次不修改服务端实现。现有服务端已经具备：

- 同缓存键只创建一个 DivineAPI 上游请求；
- 前台每次最多等待 8 秒；
- 上游请求继续在后台运行，硬上限为 35 秒；
- 成功后完成契约校验并写入缓存；
- 有真实陈旧缓存时优先返回陈旧缓存，而不是本地内容。

每位进入 pending 状态的用户最多增加三次同键 tRPC 查询，但不会增加 DivineAPI 上游调用次数。查询有明确上限，并会在页面切换或卸载时取消后续计时器。

## 测试设计

### Hook 测试

- pending 本地结果会立即安排第一次静默复查，不再等待 18 秒。
- 任一次静默查询获得 DivineAPI 时，立即原位升级且 `loading` 始终为 `false`。
- 连续 pending 时最多执行三次静默复查，之后停止。
- 普通本地降级 `providerRefreshPending: false` 不自动重试。
- 切换周期、范围、资料、手动刷新和组件卸载后，旧链路不能继续或覆盖新状态。
- 不触发十二星座排行预热。

### 组件与样式测试

- pending 本地内容显示“真实星座内容更新中，将自动替换”。
- 普通本地降级仍显示“Holaday 本地提示”。
- provider 内容显示 DivineAPI 来源，不保留更新中提示。
- 动态状态有可访问的 polite live region；减弱动画偏好下不播放呼吸动画。

### 回归与上线验证

- Web 全量测试、lint、typecheck、build 全部通过。
- Orchestrator 全量测试、typecheck、build 全部通过，证明共享路由类型和服务端契约未受影响。
- 生产环境选择一个未缓存的周期或范围，不点击刷新：先看到本地内容和“自动替换”状态，随后在供应商完成时自动切换为 DivineAPI。
- 切换过程中无第二次骨架屏、无滚动跳动、无控制台错误。
- healthz、PM2、生产 bundle 和 P0 smoke 按现有发布门禁验收。

## 非目标

- 不引入 SSE、WebSocket、消息队列或持久化 provider job。
- 不修改 DivineAPI 请求参数、Translator 或 OpenAI 配置。
- 不扩大到星座预览、排行、塔罗、小游戏或今日能量其他视觉模块。
- 不把普通供应商失败伪装成“仍在更新”。
