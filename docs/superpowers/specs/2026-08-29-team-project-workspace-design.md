# Holaday 团队项目空间与收益结算总体设计

日期：2026-08-29
状态：已完成产品与架构讨论，等待书面规格确认
范围：将现有个人项目分组升级为团队项目空间，并定义组织权限、任务闭环、验收仲裁、Holaday 协助、平台级收益积分、自动总结与管理分析的总体架构。

## 1. 背景

当前 `projects` 只是用户个人拥有的任务分组：一个项目归属于一个用户，项目页主要提供名称、描述和任务数量，任务通过 `project_id` 关联。它无法表达公司、部门、上下级、项目成员、任务认领、多人审批、奖励预算或组织级报告。

新的“项目”应成为 Holaday 的团队协作入口：上级可分配任务，员工可认领公开任务，双方在创建任务前明确交付和验收标准；员工可使用 Holaday 执行部分工作，提交结果后由上级验收，Holaday 负责整理证据、总结、风险和改进建议。项目还可以配置真实奖励，但 Holaday 不替代管理者、劳动仲裁者或支付监管机构作出最终人事决定。

该范围跨越组织协作、任务工作流、AI 执行、收益账本、结算和分析多个子系统，不能作为一个大版本一次上线。本文是总体设计；实施必须按第 17 节拆分为独立阶段，每个阶段分别验证和发布。

## 2. 目标与成功标准

### 2.1 产品目标

- 让老板、主管和员工在同一项目空间中完成“规划、分配、执行、提交、验收、复盘”。
- 让任务在开始前就具备清楚、可验证、不可事后随意更改的验收标准。
- 允许员工使用 Holaday 协助完成任务，并明确记录 AI 做了什么、消耗多少、哪些内容由人修改。
- 用公平、可申诉的流程处理质量不过关和恶意不通过，避免单方无限返工。
- 建立与 Holaday 通用积分完全分离的平台级收益积分，为团队奖励、个人悬赏、创作者分成等真实业务来源提供统一余额。
- 让管理者看到项目风险和协作问题，而不是把项目空间变成员工监控和公开羞辱工具。

### 2.2 可验收结果

1. 一个用户可加入多个组织和项目；每个组织内角色、直属上级和项目负责人均可明确表达。
2. 任务可被指派、公开认领或由 Holaday 协助，且在发布前冻结验收标准、截止时间、奖励规则和审批链。
3. 按时提交与质量通过分别记录；按时但不合格不得自动视为完成。
4. 驳回必须绑定具体标准和证据；员工可申诉，重复驳回可升级至无利益冲突的上级或指定仲裁人。
5. 收益积分只能由真实任务、悬赏、分成或活动订单产生，不支持任意个人对个人转账。
6. 自动总结可由原始任务事件和交付证据重建；AI 建议不会自动触发升降职、处罚或奖金扣回。
7. 业务协作故障不会破坏资金账本；结算故障不会丢失任务事实或重复发奖。

## 3. 非目标

- 不建设通用即时通讯或复制企业微信、钉钉的全部能力。
- 不提供员工在线时长、键鼠次数、摄像头、私人聊天或情绪监控。
- 不把收益积分做成可交易资产、投资产品、自由转账钱包或二级市场。
- 不以积分替代基本工资、加班工资、法定福利或其他应付劳动报酬。
- 不允许 Holaday 自动作出解雇、降职、处罚、劳动争议裁决或敏感人事结论。
- 首期不建设 Holaday 自有支付牌照；任何现金出款能力必须经过支付合规律师、财税人员和渠道准入共同确认。
- 不在同一阶段同时上线组织、仲裁、现金奖励、多渠道出款和完整分析。

## 4. 核心术语

- **组织**：公司或团队的权限与数据边界。
- **组织角色**：所有者、管理员、主管、成员。
- **直属上级**：成员在组织内默认的任务审批与升级路径，一个成员默认只有一个直属上级。
- **项目负责人**：项目范围内的交付负责人，不等同于组织管理员或直属上级。
- **验收合约**：任务发布时冻结的交付物、质量标准、证据、截止时间、审批链、返工上限和奖励规则。
- **Holaday 通用积分**：用于购买或消耗 AI 能力，价值可随套餐、成本和促销变化，不可提现。
- **Holaday 收益积分**：固定面值的平台级可提现权益，建议 `1 收益积分 = 税前人民币 1 元`，与通用积分永不互换。
- **归属**：收益积分在验收或其他真实业务条件满足后成为收款人的确定权益。
- **奖励资金专户**：Holaday 为未结算收益单独管理的资金账户，不与订阅、AI 服务和公司运营资金混同。

## 5. 组织、成员与权限

### 5.1 组织角色

| 角色 | 主要权限 |
| --- | --- |
| 所有者 | 组织设置、管理员任命、资金与最终治理 |
| 管理员 | 成员、部门、角色、模板、合规设置 |
| 主管 | 分配任务、验收直接下属工作、查看授权项目报告 |
| 成员 | 领取或执行任务、提交、申诉、查看自己的报告与收益 |

角色只提供默认权限。项目可另设负责人、审批人、观察者和仲裁人，但不能突破组织数据边界或利益冲突规则。

### 5.2 组织关系

- 一个成员可加入多个组织和多个项目。
- 一个成员在同一组织内默认只有一个直属上级；临时代理必须有起止时间和审计记录。
- 项目负责人可以不是成员的直属上级。
- 高奖励或敏感任务不能由同一人同时创建、执行和最终验收。
- 审批人或仲裁人与任务结果存在直接利益关系时必须回避。
- 成员离职或退出组织时，系统撤销访问权限、转交未完成任务和文件，但保留组织依法需要的审计记录。

## 6. 项目空间信息架构

项目空间使用一个统一外壳，根据权限呈现不同入口：

- **概览**：项目目标、里程碑、风险、待决策事项和下一步。
- **任务**：我的任务、待认领、团队任务、阻塞、待验收。
- **成员**：职责、负载、技能与当前阻塞，不展示无关私人数据。
- **文件**：项目交付物、证据、版本和访问权限。
- **报告**：阶段总结、周报、项目复盘与个人成长视图。
- **奖励**：奖励预算、冻结、归属、争议和结算状态。
- **设置**：角色、模板、审批链、通知和数据保留规则。

主管默认进入“项目驾驶舱”，优先看到风险、待验收、成员负载和预算；成员默认进入“我的工作”，优先看到下一步、截止时间、验收标准、Holaday 可协助项和预计奖励。

## 7. 任务生命周期

### 7.1 状态模型

```text
draft
  -> ready
  -> assigned | claimable
  -> accepted_by_member
  -> in_progress
  -> blocked
  -> submitted
  -> in_review
  -> revision_requested
  -> resubmitted
  -> accepted
  -> completed
```

附加终态：`cancelled`、`rejected_final`、`archived`。申诉是独立状态覆盖：`appeal_open`、`appeal_reviewing`、`appeal_resolved`。

### 7.2 发布前可验收化

任务发布前，Holaday 检查：

- 目标是否模糊或相互矛盾。
- 是否缺少交付格式、数量、时间范围或证据。
- 质量标准是否能够由交付物验证。
- 是否存在“做到满意为止”等无限责任表述。
- 审批人、仲裁人、奖励和截止时间是否完整。

Holaday 可生成建议，但创建者必须确认后才能发布。验收合约按版本保存；发布后的需求变更必须形成新版本，并同步调整截止时间、工作量和奖励，旧版本不得覆盖或删除。

### 7.3 指派与认领

- 指派任务：主管选择成员，成员确认接收或提出负载冲突。
- 公开认领：符合角色、技能、容量和地域限制的成员可以申请；可设置先到先得或负责人选择。
- 多人协作：明确负责人、协作者、各自交付和奖励分配规则。
- Holaday 执行：员工可将可自动化部分交给 Holaday，但最终提交人对结果负责。

系统只提供负载、技能和截止冲突建议，不根据在线时长或操作频率自动判定员工是否努力。

### 7.4 阻塞与变更

- 上游未交付、权限缺失、资料缺失、系统故障和需求冲突均可进入 `blocked`。
- 阻塞必须指定责任方、下一动作和复查时间。
- 若阻塞并非执行人责任，截止时间不会自动倒计时处罚；是否延期由预设规则或负责人确认。
- 范围增加必须增加时间或奖励，不能在验收阶段追溯新增标准。

## 8. 提交、验收与仲裁

### 8.1 时间与质量分离

- `submitted_on_time` 只说明按时提交，不代表质量通过。
- `accepted` 说明满足验收合约。
- 按时奖励只有在质量最终通过后才生效，避免通过低质量占位提交获取奖励。
- 阶段交付通过后，其对应奖励可独立归属，不因后续阶段争议全部扣回。

### 8.2 驳回规则

每次驳回必须包含：

1. 未满足的验收标准编号。
2. 对应交付证据或缺失证据。
3. 可执行的修改要求。
4. 新的提交期限。

无理由驳回、只写“质量不行”或在验收时新增标准均被系统阻止。默认最多两轮返工；任务创建时可以在合理范围内调整，但必须让执行人领取前知晓。

### 8.3 混合仲裁

- 客观任务先由确定性规则和 Holaday 证据预检，再由人确认。
- 主观任务由主管首次验收，员工可针对事实或规则提出一次正式申诉。
- 连续两次驳回或提出申诉后，升级至上一级主管或预先指定的独立仲裁人。
- 小组织必须预设替代仲裁人；高奖励任务可要求两名独立审批人。
- 审批超时自动提醒并升级，不能无限拖延。
- Holaday 负责整理双方主张、标准、版本和证据，只给建议，不作最终处罚决定。

## 9. Holaday 协助与责任归属

每次 AI 协助必须记录：

- 用户要求 Holaday 完成的范围。
- 输入资料、来源和时间。
- 生成或执行结果及其版本。
- 消耗的通用积分或额度。
- 人工修改、删除或确认的部分。
- 未验证事实、风险和失败步骤。

禁止只以任务状态 `Completed`、文件存在、哈希或模型自评作为完成证据。交付报告必须把结论绑定到来源、原始摘录、时间和 `observed / extracted / inferred` 证据等级；结构化交付物还需要确定性 schema 校验。

## 10. 收益积分与奖励资金

### 10.1 两种积分完全分离

| 项目 | Holaday 通用积分 | Holaday 收益积分 |
| --- | --- | --- |
| 用途 | 消耗 AI 能力 | 真实任务、分成和活动收益 |
| 价格 | 可随套餐变化 | 固定人民币面值 |
| 提现 | 不支持 | 达到归属和结算条件后支持 |
| 相互兑换 | 不允许 | 不允许 |
| 账本 | 消费与额度账本 | 独立收益与资金负债账本 |

前端使用不同名称、图标、色彩、余额入口和流水。充值优惠不得改变收益积分面值，也不得制造充值提现套利。

### 10.2 平台级来源

收益积分可来自：

- 企业团队任务。
- 个人发布的真实悬赏任务。
- 创作者内容分成。
- 合规推荐佣金。
- 广告或平台活动收益。

前端可展示统一余额，后台必须按 `source_type`、付款方、业务订单、归属规则、税务类别和结算周期分账。不同来源不得在账本中丢失其经济背景。

### 10.3 首期资金模式

采用已确认的 Holaday 自营奖励结算模式：

1. 企业或个人为真实业务充值奖励预算。
2. 资金进入 Holaday 奖励资金专用账户，财务记录为待结算负债，不计入可自由使用的经营现金。
3. 到账回调确认后，系统才生成等额收益积分。
4. 任务发布时冻结奖励；任务取消或未成立时按规则释放。
5. 验收通过后，收益积分归属收款人，付款方不能单方撤销。
6. 提现日前，财务根据银行、微信、支付宝渠道汇总，从奖励专户向对应出款账户调拨已有资金。
7. 系统确认渠道资金充足后，通过 API 批量出款并对账。

任何阶段均不开放无业务背景的个人对个人转账。未分配余额只能原路退回充值人；已归属余额只能付给实名收款人。

### 10.4 收益状态

```text
unallocated       已充值、尚未分配
reserved          已绑定任务或业务订单
vesting           条件尚未全部满足
withdrawable      已归属、可进入结算
pending_payout    已冻结等待出款
paid              已到账
failed            出款失败，可重试或退回可提现
frozen            风控或争议冻结
reversed          合法撤销并留下反向账目
```

资金守恒式：

```text
未分配 + 已冻结 + 归属中 + 可提现 + 待出款
<= 奖励专户及各出款通道可核验资金
```

系统每日执行账本、支付渠道和银行流水三方对账；不一致时停止新收益积分发行和新出款，不修改既有历史流水。

### 10.5 定期奖励与留任

- 已归属任务奖励建议按季度结算，不能因员工随后离职而清零。
- 年终留任奖励是额外加成，不得以扣留已获得奖励的方式实现。
- 年度加成在条件满足前属于未归属权益，规则必须事先公示。
- 基本工资、加班工资和法定待遇不能由收益积分替代。

### 10.6 多渠道提现

- 银行卡：实名银行卡、银行或代发接口。
- 微信：申请商家转账权限，按真实场景报备，支持确认收款或授权后的免确认收款。
- 支付宝：申请商户转账能力，按准入场景、实名和限额执行。

每个渠道适配器只负责提交、查询、回调验签和回单；结算核心统一负责 KYC、税费、限额、幂等、冻结和状态机。用户首次绑定、更换渠道或高风险提现需要额外验证和冷静期。

现金能力上线前必须完成书面支付合规意见、财税流程、奖励专户、渠道准入、隐私评估、对账演练和失败回滚。若自营模式被认定涉及受许可支付业务，则该阶段改用持牌合作方，不通过产品命名规避监管。

## 11. 自动总结、分析与报告

### 11.1 四层报告

- **任务报告**：交付物、标准映射、证据、返工、AI 参与和成本。
- **项目报告**：进度、里程碑、风险、阻塞、预算、成员负载和下一步。
- **个人成长报告**：优势、常见问题、擅长任务、改善趋势和建议。
- **组织报告**：整体通过率、延期原因、返工模式、协作瓶颈和 AI 投入产出。

### 11.2 生成节奏

- 严重阻塞、延期风险、资金异常和验收争议即时提醒。
- 普通进展汇总为周报，不制造每日信息噪音。
- 里程碑完成后自动生成阶段复盘。
- 项目结束后生成最终总结，由负责人确认后上报。

### 11.3 双层权限

- 员工看到完整个人成长报告，并可更正事实错误。
- 主管只看到与工作交付直接相关的证据、趋势和改进建议。
- 不分析私人对话，不推断情绪、人格、家庭情况或健康状态，不统计无业务必要的在线时长。
- AI 建议必须标明依据与不确定性，不自动决定晋升、降职、处罚或奖励扣回。
- 原报告、人工修改和重新生成记录均保留版本。

## 12. 总体架构：方案乙双核心

### 12.1 协作核心

继续由 Orchestrator 承担：

- 组织、成员、角色和权限。
- 项目、里程碑、任务和依赖。
- 指派、认领、提交、验收和申诉。
- Holaday 执行与证据记录。
- 自动总结、项目分析和管理看板。

内部按领域拆为独立模块，首期不拆成多个网络微服务。现有 `task_events` 可作为任务审计基础，但团队项目事件需要明确租户、操作者、版本和幂等键。

### 12.2 结算核心

由独立收益结算边界承担：

- 收益资金充值与资金批次。
- 收益积分双重记账、冻结、归属和撤销。
- KYC、风险、限额和争议冻结。
- 结算日、渠道资金预测和出款路由。
- 银行、微信和支付宝适配器。
- 对账、退款、回单和审计。

可从现有 `cn-payment`、Partner Ledger 和提现能力演进，但不得直接把旧 HOLA Credit、API Units 或通用积分重新命名后混用。旧账本保持不变，新收益账本独立建立；是否迁移旧余额必须在余额核对和单独规格确认后执行。

### 12.3 事件连接

协作核心与结算核心通过事务性 outbox/inbox 连接：

```text
reward.reserve.requested
reward.reserved
```

## 13. 关键数据边界

本文只规定领域对象，不固定最终表名：

- `organizations`、`organization_members`、`reporting_lines`。
- `team_projects`、`project_members`、`project_milestones`。
- `work_items`、`work_item_assignees`、`acceptance_contract_versions`。
- `submissions`、`reviews`、`appeals`、`arbitration_decisions`。
- `work_item_events`、`evidence_bindings`、`ai_contributions`。
- `earnings_accounts`、`earnings_lots`、`earnings_ledger_entries`。
- `reward_reservations`、`vesting_events`、`payout_orders`、`payout_attempts`。
- `payout_destinations`、`reconciliation_runs`、`funding_transfers`。
- `generated_reports`、`report_versions`、`report_corrections`。

所有金额使用最小货币单位整数存储；任何余额均由不可变流水汇总，不把可修改余额列作为唯一事实。敏感收款信息优先由渠道或专用凭据存储系统持有，Holaday 保存令牌、指纹和脱敏展示。

## 14. 错误处理与补偿

- 奖励冻结失败：带奖励任务保持 `ready`，不得伪装成已正式发布；创建者可明确选择移除奖励后重新发布。
- 任务事实写入成功、归属事件暂时失败：任务验收保持有效，奖励显示“待归属”并自动重试。
- 重复验收或重复回调：幂等键返回同一结果，不产生第二笔奖励。
- 报告生成失败：原始任务和证据不受影响，允许重新生成。
- 出款受理不等于成功：只有渠道终态或对账确认后才标记 `paid`。
- 出款失败：资金和积分退回可提现状态；更换渠道后生成新尝试，不复用已失败的渠道订单号。
- 三方对账不一致：冻结相关批次和新出款，保留全部原始流水，由双人复核处理。
- 需求版本冲突：提交绑定领取时确认的验收合约版本，新版本必须获得执行人确认。

## 15. 安全、隐私与治理

- 组织是服务端强制租户边界；客户端传入的组织或项目 ID 不能替代会话权限校验。
- 角色校验同时验证组织成员、项目成员和资源归属，避免仅依赖前端隐藏按钮。
- 高风险动作使用双人审批：大额奖励、退款、结算批次、规则修改和手工账本调整。
- 人工账目修正只能追加反向流水，不能更新或删除历史金额。
- 收款方式变更、设备异常、大额提现和短期高频奖励触发冷静期或人工复核。
- 任务评价与劳动报酬规则应版本化、公示并记录成员确认；正式上线前由劳动、支付与税务专业人员审核。
- 数据导出遵循最小必要原则；管理报告不得包含私人消息、原始身份证号、完整银行卡或渠道密钥。

## 16. 测试与验收策略

### 16.1 权限与组织

- 跨组织、跨项目和离职成员访问必须被拒绝。
- 临时代理到期后不能继续审批。
- 利益冲突审批人不能完成最终仲裁。

### 16.2 任务与验收

- 全状态机合法转移、非法跳转和并发提交。
- 验收版本冻结、范围变更、阻塞延期和两轮返工。
- 无理由驳回、超时升级、申诉和双审批。
- 证据、结构化 schema 和 AI 贡献记录可重建。

### 16.3 收益与资金

- 充值到账前不得发行收益积分。
- 冻结、释放、归属、争议和出款全链路双重记账守恒。
- 重复事件、重复回调、超时查询和渠道乱序回调不能重复付款。
- 通用积分与收益积分不能相互消费、兑换或被错误展示。
- 三渠道成功、失败、待用户确认、退款和回单对账。
- 资金池不足、渠道余额不足和对账差异必须阻断新出款。

### 16.4 报告与隐私

- 同一事实可从事件和证据重建报告。
- 员工完整视图与主管工作视图字段隔离。
- 敏感文本和私人内容不会进入管理报告提示词或导出。
- AI 报告错误可更正，原版本和更正记录可追溯。

## 17. 分阶段实施

### 阶段一：组织与团队项目基础

- 组织、角色、直属上级、项目成员和权限。
- 项目空间外壳、项目概览、成员和任务入口。
- 兼容迁移现有个人项目，不破坏已有任务和文件。

上线条件：租户隔离、权限矩阵、旧项目迁移和生产回滚验证通过。

### 阶段二：任务闭环与验收仲裁

- 指派、认领、里程碑、依赖、阻塞和验收合约。
- 提交、返工、申诉、仲裁、审批 SLA 和证据包。
- Holaday 协助记录和交付预检。

上线条件：所有状态机、并发、版本和仲裁测试通过。

### 阶段三：收益积分预留与归属

- 新的独立收益账本。
- 使用沙箱资金事件或平台内部白名单测试奖励冻结、释放、归属和争议冻结。
- 建设项目奖励预算和员工收益页面，但不向外部客户开放真实资金充值，也不承诺真实提现。
- 在阶段四完整结算链路通过前，禁止形成“真实充值已到账但用户无法提现”的单边资金状态。

上线条件：资金守恒、账本幂等、通用积分隔离、审计和人工对账通过。

### 阶段四：定期结算与多渠道出款

- 奖励专户、财务调拨单和渠道余额确认。
- 对外开放真实奖励资金充值、等额收益积分发行和归属。
- 银行卡、微信、支付宝出款适配器。
- KYC、税费、限额、回单和三方对账。

上线前置：书面支付合规意见、财税方案、渠道权限、隐私评估和生产小额白名单演练全部通过。任一前置缺失时不得开放真实资金。

### 阶段五：报告与组织洞察

- 任务、项目、个人和组织四层报告。
- 事件触发风险提醒、周报、里程碑复盘和终期总结。
- 双层权限、事实更正和 AI 投入产出分析。

上线条件：报告可追溯、权限隔离、敏感数据最小化和人工抽样准确率通过。

## 18. 上线、迁移与回滚原则

- 使用组织级功能开关逐步启用，不把所有个人项目自动转换为团队项目。
- 旧个人项目默认保持原行为；用户主动创建组织或迁移项目时才进入新模型。
- 每个阶段独立迁移、独立部署、独立生产验证和独立回滚。
- 资金迁移只允许在余额逐项核对、双人批准和可逆演练后进行。
- 任何回滚均不能删除任务事件、验收证据、收益流水或出款回单。
- 收益和出款能力先对内部白名单组织开放，再扩大到受邀企业，最后才评估平台级开放。

## 19. 已确认决策摘要

- 组织角色采用所有者、管理员、主管、成员；直属上级与项目负责人分离。
- 任务支持指派与认领，并在发布前冻结验收合约。
- 按时提交不等于质量通过；采用两轮返工、强制理由、申诉和独立仲裁。
- Holaday 整理证据和建议，不作最终人事处罚决定。
- 奖励采用平台级 Holaday 收益积分，与通用积分完全隔离。
- 收益积分固定人民币面值，只允许真实业务奖励，不开放任意个人转账。
- 首期采用 Holaday 自营奖励结算、独立奖励资金专户和财务按渠道调拨。
- 已获得奖励与年终留任加成分离，不能用扣留既得奖励留人。
- 报告采用员工完整视图、主管工作视图，不建设情绪或在线监控。
- 总体架构采用方案乙：Orchestrator 协作核心 + 独立收益结算核心。
