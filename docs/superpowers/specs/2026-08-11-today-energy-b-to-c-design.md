# HOLA DAY 今日能量 B 阶段设计

## 1. 决策与目标

当前先实施 B：把“今日能量”从星座内容长页面重构为面向 Staff 的轻量情绪陪伴与休息入口。用户应能在工作间隙快速完成一次状态签到，获得一句鼓励和一个可立即参与的轻体验。抽卡、心理测试、今日星座和未来小游戏是平级玩法，不再由“多元化命理”代表整个板块。

未来内容、活动和小游戏供给成熟后，再演进到 C：可运营的内容与轻游戏中心。B 阶段必须留下清晰扩展接口，但不提前建设完整内容后台、奖励经济、社交排行或复杂运营系统。

本阶段成功标准：

1. 用户进入页面后能在一个首屏内理解用途，并在一次选择内开始体验。
2. 首页始终只突出一个推荐行动，不再同时展示多个同等优先级的大区块。
3. 抽卡、测试、星座和小游戏共享统一的进入、进行、完成和重玩模型。
4. 现有星座、塔罗、状态测试和周节奏能力得到保留，但重新编排层级。
5. 前端不再由单个接近 2,000 行的组件承担页面编排、玩法状态、持久化和结果展示。

## 2. 用户与使用情境

核心用户是使用 HOLA DAY 完成日常工作的 Staff。典型情境包括：

- 等待任务执行时想短暂放松；
- 工作开始前需要一个温和的启动动作；
- 感到疲惫、焦虑、堵塞或缺少动力时，希望得到情绪价值；
- 午休或工作间隙想玩一个几十秒到几分钟的轻体验；
- 想查看今日星座、抽卡或做一个轻测试，但不想阅读一整页信息。

默认体验时长分为三档：30 秒、1 分钟和 3 分钟。B 阶段不引入超过 5 分钟的主流程。

## 3. 产品定位与文案边界

板块对外定位为“工作间隙的轻松陪伴”，而不是专业心理诊断、人生决策工具或纯命理中心。

文案原则：

- 使用鼓励、陪伴、提醒和建议语气，不使用确定性预言；
- 不根据轻测试结果给出疾病、人格障碍或心理健康诊断；
- 不制造焦虑、恐惧、运势惩罚或付费解锁压力；
- 建议必须轻量、可执行，例如喝水、深呼吸、离开屏幕、写下一个小步骤；
- 星座、塔罗和数字内容明确保持娱乐与自我反思属性；
- 当用户选择明显低落或压力大的状态时，结果以安抚和休息建议为主，不强制把用户推回工作任务。

## 4. 信息架构

`/cosmic` 路由和侧边栏“今日能量”名称保持不变。页面内部采用以下结构：

```text
今日能量
├── 状态签到
├── 今日回应
├── 今日推荐
├── 玩法入口
│   ├── 抽张卡
│   ├── 轻测试
│   ├── 今日星座
│   └── 小游戏
└── 我的能量
    ├── 个人资料
    ├── 最近体验
    └── 收藏结果（P2）
```

首页不再顺序展开个人档案、五类运势、心理测试和七日节奏。非当前任务的内容进入抽屉、独立体验容器或折叠详情。

## 5. 首页体验

### 5.1 首屏

首屏只保留三个层次：

1. 标题和一句轻量说明；
2. 状态签到：“你现在感觉怎么样？”；
3. 今日回应与一个推荐行动。

状态选项首版使用四个互斥值：

- `状态不错`
- `有点累`
- `压力有点大`
- `只想放空`

未选择时，页面展示中性欢迎语和今日推荐。选择后，在原位置更新一句鼓励、一个轻建议和一个主按钮，不新增纵向区块。

状态选择只用于本次体验推荐和匿名产品分析。B 阶段不把用户状态写入公开资料，不向管理者提供个人情绪查看入口。

### 5.2 今日推荐

每天只突出一个推荐玩法。推荐卡包含：

- 名称；
- 预计时长；
- 一句用户收益；
- 主按钮；
- 可选的“换一个”。

推荐顺序可以结合当次状态、当天日期和最近体验做确定性选择。B 阶段不建设机器学习推荐系统。

### 5.3 玩法入口

今日推荐下方展示四个紧凑入口：抽张卡、轻测试、今日星座、小游戏。入口是导航，不在首页直接展开完整结果。

小游戏在尚无正式内容时显示“即将上线”，但不得使用不可点击的假按钮。首个小游戏上线后再开放该入口。

### 5.4 我的能量

个人资料从主页主体移入右侧抽屉或独立面板。用户只有在需要增强星座内容时才填写生日、出生时间和地点。

首版资料规则：

- 昵称可选；
- 生日仅在星座玩法需要时请求；
- 出生时间、出生地属于深度星盘信息，默认隐藏在“完善星象资料”二级动作下；
- 每个字段解释用途；
- 继续沿用按用户隔离的本地存储，服务端持久化另行设计并取得明确同意后再做。

## 6. 统一体验容器

所有玩法进入统一的 `ExperiencePlayer`，桌面端使用页面内覆盖层或宽抽屉，窄屏使用全屏页面。它必须有一致的四段状态：

```ts
type ExperiencePhase = 'intro' | 'active' | 'result' | 'error';
```

- `intro`：说明玩法、预计时长、是否需要资料；
- `active`：用户做选择、抽卡或游戏操作；
- `result`：展示结果、鼓励、重玩和返回；
- `error`：保留退出与重试，不丢失已完成的选择。

结果不得在用户完成互动前提前显示。重新体验必须重新进入 `active`，不能只替换结果文案。

完成页统一提供：

- `再来一次`
- `换个玩法`
- `回到今日能量`
- `这对我有帮助`（P2）

复制和收藏是次要动作，不与主流程争夺视觉优先级。

## 7. B 阶段玩法定义

### 7.1 抽张卡

抽卡由“选择关注主题 → 抽取 → 翻牌 → 结果”组成。主题首版为“工作节奏、关系沟通、给自己一点空间”。每日塔罗接口可以继续作为内容来源，但抽取动作和结果展示由体验容器负责。

结果包括：牌名或卡名、一句核心提示、一段解释和一个轻行动。娱乐属性需要在 intro 或结果页以低噪声方式说明。

### 7.2 轻测试

首版保留一个 3 题以内的状态测试，不再默认预选答案或提前展示结果。测试定义与结果映射从组件中提取为独立数据。

结果包含：温和标签、状态解释、一个优势、一个提醒和一个轻行动。不得使用临床标签。

### 7.3 今日星座

首页只显示星座名称、一句今日提示和“查看详情”。详情页通过分段切换查看总览、工作、人际、财务和身心，禁止再次使用五个窄列承载长文。

周节奏移入星座详情的二级标签，不再占据主页底部。个人档案由星座体验按需打开。

### 7.4 小游戏

B 阶段只定义容器接口，不建设完整游戏中心。首个游戏应满足：

- 30 秒到 3 分钟可完成；
- 无付费、无排名压力、无无限体力循环；
- 支持键盘和指针操作；
- 可独立懒加载；
- 结束后返回统一结果页；
- 不访问星座资料，除非玩法明确说明且用户同意。

适合的第一批方向包括呼吸节奏、颜色匹配、轻记忆和一笔整理，不做高刺激或长时间沉迷玩法。

## 8. 前端架构

保留 `AstrologyPage` 作为兼容入口，但页面编排改由能量域承担：

```text
components/energy/
├── EnergyHome.tsx
├── MoodCheckIn.tsx
├── DailyResponse.tsx
├── RecommendationCard.tsx
├── ExperienceCatalog.tsx
├── ExperiencePlayer.tsx
├── EnergyProfileDrawer.tsx
├── experience-registry.ts
├── experience-types.ts
└── experiences/
    ├── tarot/
    ├── psychology/
    ├── horoscope/
    └── games/
```

每个玩法通过注册表声明能力：

```ts
interface EnergyExperienceDefinition {
  id: string;
  kind: 'card' | 'test' | 'horoscope' | 'game';
  title: string;
  description: string;
  estimatedSeconds: number;
  status: 'active' | 'coming-soon' | 'hidden';
  requiredProfileFields: Array<'birthday' | 'birthTime' | 'birthPlace'>;
  load: () => Promise<{ default: React.ComponentType<EnergyExperienceProps> }>;
}
```

注册表负责发现、排序和懒加载，不负责具体玩法状态。玩法只能通过统一回调报告开始、完成、重玩、退出和错误。

现有 `AstroDashboard.tsx` 不做一次性机械拆分。迁移顺序是：先建立新首页和容器，再逐个搬迁玩法，最后删除旧编排组件。`lib/astrology.ts` 只保留星座领域数据和纯函数，通用体验状态、存储键和推荐逻辑迁到 `energy` 域。

## 9. 服务端边界

B 阶段新增 `energy` 聚合路由，但复用现有 `astrology` 服务：

```ts
energy.home.query()
energy.experience.start.mutate({ experienceId, mood })
energy.experience.complete.mutate({ sessionId, outcome })
energy.experience.feedback.mutate({ sessionId, helpful }) // P2
```

`energy.home` 返回可用玩法、今日推荐和功能开关。星座与塔罗数据继续由现有 provider adapter 提供。客户端不直接依赖第三方 provider 名称。

P1 可以只对开始和完成事件做低敏统计，不保存具体测试答案或情绪文本。若事件持久化需要新表，应使用独立迁移，并在实施计划中明确数据保留和删除策略。

## 10. 面向 C 的扩展接口

B 只预留以下接口：

- 玩法注册信息支持上下线、排序和版本；
- 玩法资源支持懒加载；
- 体验事件使用稳定 ID；
- 首页编排只依赖聚合响应；
- 结果模型可以附带收藏和反馈状态。

C 成熟阶段再建设：

- 内容与活动后台；
- 分人群和时间段的推荐编排；
- 内容审核与版本发布；
- 游戏资源管理；
- 连续使用激励；
- 运营分析看板。

C 不默认包含排行榜、员工间情绪比较、管理者查看个人状态或货币化奖励。这些能力需要单独的伦理与隐私评审。

## 11. 状态、错误与降级

- 首页聚合失败：展示本地中性欢迎语和可离线运行的轻测试，不显示空白页；
- 星座或塔罗 provider 失败：保留现有确定性本地内容，并明确“暂时使用本地提示”；
- 玩法动态加载失败：停留在体验容器，显示重试和返回；
- 本地存储不可用：允许继续体验，不保存资料和最近选择；
- 重复点击开始：同一容器只创建一个活动会话；
- 用户退出未完成体验：不计为完成，也不弹阻塞式确认；
- 小游戏异常：隔离在游戏体验边界，不影响首页和其他玩法。

## 12. 可访问性与响应式要求

- 所有互斥选择使用单选语义、`aria-pressed` 或等价状态，不只依靠颜色；
- 键盘可以完成状态签到、测试、抽卡和退出；
- 焦点进入体验容器后被正确管理，关闭时返回启动按钮；
- 结果变化使用适度的状态播报，不自动朗读整段长文；
- 触控目标不小于 44×44 CSS 像素；
- 动效遵循 `prefers-reduced-motion`；
- 桌面首屏不超过一个主滚动视口；
- 窄屏改为单列，不把长文压进多列卡片；
- 200% 缩放下仍能完成核心流程。

## 13. 数据与指标

核心事件：

- `energy_home_viewed`
- `energy_mood_selected`
- `energy_experience_started`
- `energy_experience_completed`
- `energy_experience_replayed`
- `energy_experience_failed`
- `energy_feedback_submitted`（P2）

事件只包含稳定玩法 ID、时长档位、宽泛状态枚举、完成状态和客户端版本。不得上传生日、出生地、测试答案正文、自由文本或可用于员工情绪监控的个人明细。

首要指标：玩法启动率、完成率、次日再次访问率和“有帮助”比例。停留时长只用于发现卡顿或中断，不作为鼓励沉迷的目标。

## 14. 实施阶段

### P0：页面收口

- 建立新首页层级；
- 状态签到前置；
- 合并重复的今日提示和任务等待模式；
- 星座五类运势改为分段详情；
- 个人档案移入抽屉；
- 保留旧玩法能力，不新增数据库。

### P1：结构重构

- 建立 `energy` 目录、玩法注册表和统一体验容器；
- 迁移抽卡、心理测试和星座；
- 加入统一开始、完成、退出和错误事件；
- 删除旧页面编排和重复本地存储逻辑；
- 建立组件、交互和可访问性测试。

### P2：体验闭环

- 最近体验；
- 结果收藏；
- “有帮助”反馈；
- 推荐去重；
- 服务端最小化事件持久化与保留策略。

### P3：第一批小游戏

- 接入独立游戏体验包；
- 验证懒加载、键盘操作、异常隔离和统一完成页；
- 依据启动率、完成率和反馈决定是否进入 C。

## 15. 测试与验收

### 自动化

- 首页编排：未选择状态、选择后回应、推荐切换和 coming-soon；
- 体验容器：四段状态、关闭焦点恢复、重玩、错误恢复；
- 每种玩法：intro 前不显示结果，完成后结果与选择一致；
- 注册表：ID 唯一、状态过滤、按需资料和动态加载失败；
- 存储：用户隔离、不可用降级、旧键迁移；
- 服务端：鉴权、输入校验、provider 降级、事件最小化；
- 可访问性：互斥状态、名称、焦点和键盘路径；
- 响应式：桌面、平板、手机和 200% 缩放。

### 浏览器验收

1. 从 `/cosmic` 进入，首屏看到状态签到和一个推荐；
2. 选择四种状态中的任意一种，回应原位更新；
3. 启动抽卡，完成翻牌并返回首页；
4. 启动轻测试，回答前看不到结果，完成后可重玩；
5. 查看星座详情并切换五类内容；
6. 打开和关闭个人资料，焦点正确返回；
7. 在窄屏和键盘模式下完成同样路径；
8. provider 失败时仍能使用本地内容；
9. 全流程无控制台错误、框架覆盖层或数据串号。

## 16. 非目标

B 阶段不包含：

- 完整内容运营后台；
- 排行榜、Staff 间比较或管理者情绪监控；
- 付费抽卡、虚拟币、体力或随机奖励经济；
- 专业心理咨询、诊断或危机干预替代；
- 复杂个性化算法；
- 社交分享流和公开结果；
- 一次性重写现有星座 provider。

## 17. 发布门槛

B 阶段只有在以下条件同时满足时才可上线：

- P0 与 P1 的核心流程完成；
- 现有星座和塔罗能力没有回归；
- 抽卡、测试、星座至少三类玩法都通过统一容器；
- 桌面和窄屏浏览器验收通过；
- 键盘主流程与选中状态语义通过；
- 不上传个人情绪明细或出生资料；
- 生产环境降级路径经过验证；
- 相关测试、类型检查、构建和差异检查通过。

C 的建设决策依据 P2/P3 的真实使用数据单独评审，不与 B 同批实施。
