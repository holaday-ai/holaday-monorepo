# 浏览器候选：停机维护与失败恢复设计

状态：用户已同意停机维护方向；本文件待审阅。未实施、未演练、未部署。

代码基线：`fa497fdedf0b479fd604f34f36b92196551fbb19`，分支 `codex/browser-release-candidate-20260925`。线上 `107857fe70503e30691073f267d87275596edb20` 只是此前只读预检记录，实施切换前必须重新核实。

## 1. 目的与边界

把候选版本的维护发布收成一项可验收的工作：停止接纳新任务，让已接纳的执行完成，保留暂停及待用户确认的数据；候选失败后不让不兼容旧代码处理新格式任务或未知费用。

用户已接受停机维护，优先级仍为浏览器任务能力、操作体验、能力边界。本项不扩展浏览器功能，不建设零停机发布、原生池、通用运维平台或新的任务调度器。维护验收通过不等于浏览器成功率达标，也不替代多页、上传、Canvas 和代表性同题任务验收。

本次设计和后续本地实现不授权推送、合并、生产停机、生产 SQL、修改生产配置、安装扩展或取消用户任务。生产切换仍单独停下核对范围。

## 2. 方案取舍

采用**维护关闭期间升级，失败维持关闭，兼容修复后重新验收**。

- 不选热切换：用户接受停机，双版本同时运行及调度归属切换会增加本次范围。
- 不选自动退回原线上版本：旧版把 NULL 费用读成 0，且不理解新执行身份；健康检查成功不能证明业务兼容。
- 不制作一套“删除新字段、改写新任务”的数据降级逻辑。也不把整库备份恢复当作默认回退，因为维护期间其他服务仍可能写入支付等业务数据。

现有受控池 `DrainController` 与原生启动身份、持久状态和开放许可绑定，普通启动没有这套能力。本项不能通过伪造 `ApplicationBoot`、补一个恒真 `authorizeOpen` 或移除原生校验接入。普通维护协调与受控池保持分离；可复用已验证的生命周期原语，但不能把原语的局部计数称为全进程排空证明。

## 3. 当前代码约束

| 位置 | 已核对的行为 | 设计约束 |
| --- | --- | --- |
| `scripts/orchestrator-runtime.sh` | 重启直接删除 PM2 进程，另有强制停止路径 | 维护切换不能先调用这个重启流程再检查任务 |
| `scripts/deploy-orchestrator.sh` | 多种失败自动恢复旧 checkout、构建、重启；SQL 不撤销 | 候选启动或迁移开始后的失败默认保持维护，不调用旧自动回退 |
| `application-main.ts` | 普通启动运行计划轮询与任务恢复；普通停机没有先停止全部派发源 | 关闭状态必须在启动副作用之前生效；关监听端口不是停止派发 |
| `scheduled-runner.ts`、`planned-runner.ts` | 现有 stop 等待本轮轮询，不等待已分离的任务执行 | 等待轮询与等待执行分别验收 |
| `ws/server-work.ts`、`ws/server.ts` | 连接关闭不证明远端扩展动作停止；回执参与任务完成 | 排空时保留原任务回执，不能先关闭全部 WS |
| `trpc/trpc.ts`、`http.ts` | HTTP 与内部 caller 不完全共用同一个入口 | 不能只在反向代理或 HTTP 中间件挡新任务 |

这些是基线源码观察，不是生产带任务停机实验。

## 4. 普通运行模式的维护契约

### 状态和控制入口

只有四个状态：`serving`（接单）、`draining`（不接新单，等待原执行）、`closed`（可以停止进程）、`blocked`（结果或覆盖不明）。

维护状态由部署操作者控制，不能由网页、扩展、任务 prompt 或普通业务 API 设置。拟采用本机 Unix socket，文件权限限定部署身份；每次控制请求匹配当前发布 SHA 与进程启动标识，旧请求不能作用于新进程。公网不新增维护管理接口。

发布维护标记保存在部署目录而非 checkout 中，原子更新，重启后仍保持关闭。已标记维护的进程不得因环境变量缺失、重启、超时或健康检查成功自动接单。状态读取失败时拒绝启动业务入口。启用新维护契约的发布必须显式配置并验证它；未接入的旧进程不能报告为已接入。

标记同时保留是否需要核对上一次未完成执行的状态；进程崩溃后不能以新进程计数为零消除旧不明结果。控制命令串行、重复关闭幂等；普通维护配置与原生受控启动元数据同时存在时拒绝混合启动，不选择较宽松的一条路径。

`beginMaintenance()` 同步关闭新的执行准入，然后停止未来轮询和自动恢复派发；`snapshot()` 返回状态与分类数量，不含用户正文、Cookie、密钥；`waitForIdle(deadline)` 仅在已跟踪工作均实际结束、无不明结果且覆盖检查通过时返回。超时只返回阻塞，不取消任务、不执行强杀、不把数量清零。

`resumeServing()` 只允许对已验收的同一候选启动实例调用。停止后重新启动的实例必须重新验收；存在 `blocked` 结果不能靠重新打开开关消除。

### 新请求与已有任务

- HTTP/tRPC、任务 webhook、内部 caller、WS 续跑/人工浏览器操作、定时与规划任务、队列派发、启动恢复均纳入入口清单。检查应发生在新建任务、扣额度和派发外部调用之前。
- 进入维护后，新任务和新续跑返回稳定的“维护中，请稍后重试”结果。禁止接收后静默丢弃，也不自动延迟到维护结束重放。
- 已接纳的整项任务可以继续它原有工作流内的步骤；新任务根不能冒充旧任务子步骤。子工作必须在异步派发前登记，外层 HTTP 返回、主 Promise 结束或数据库显示 completed 都不能提前释放仍执行的子工作。
- WS 心跳和已发送动作的回执继续处理，并绑定原用户、原连接/执行会话、原请求。旧连接上的新用户指令仍拒绝。只有实际执行及其回执结算完成，才能关闭连接和浏览器资源。
- 队列里尚未派发的项不在维护时强行启动或删除。必须证明它们已持久化、不会被当前 worker 再取出，才能作为“保留待恢复项”单独列示；做不到则阻止停机。
- `awaiting_user`、`paused` 不要求清零，不自动改成失败或完成；若其背后仍有真实执行，则仍算活动工作。恢复服务后按既有用户操作恢复，不为发布自动重放。
- 任务级未知副作用、扩展断线后动作结果不明、未结算的远端生成请求均阻止“已排空”结论。网络超时不是取消成功。预期输入校验/鉴权拒绝不应被误判成副作用不明。

### 后台与旁路

既有 `stopScheduledRunner`、`stopPlannedRunner` 用于停止新轮询，但派生任务必须独立跟踪。启动恢复、预热、清理、定期归纳、独立账号关闭 worker 分别列入覆盖清单；有状态写入或外部副作用的工作不能仅靠 `unref()` 排除。

不更改支付、额度或账号关闭业务语义。维护期不新接纳支付等业务写入，拒绝的支付回调不得回复伪成功；已接纳事务须等待结算。生产放行前必须验证回调重试/补偿安排及独立支付服务写入边界，未验证则不执行生产维护。健康检查只报告存活，另以维护状态报告是否可接单。

维护期间允许的只读检查使用逐项核对的内部检查入口，不能把所有 GET、tRPC query 或 localhost 请求视为无副作用。检查中的原始查询也必须等待完成，才能停止进程；不在维护模式调用会更新缓存、触发恢复或生成内容的所谓只读接口。

覆盖清单是验收产物，不是“全局包裹一个 Promise”即可满足的假设。若发现无从归属的执行入口，默认阻止发布，先报告确切入口与最小补齐范围，不顺势扩建原生池。

## 5. 首次旧版本切换：单独识别，绝不假装无损

当前记录的线上版本没有上述维护协议。不能把新版本的维护开关用于证明旧进程已停止接单，也不能先安装新版本再追溯证明旧任务安全结束。

发布工具先识别旧进程能力。若不支持协议，返回 `LEGACY_DRAIN_UNSUPPORTED`，在任何迁移、替换或停进程动作前停止。普通部署不能用环境变量跳过此结果。

首次引导是明确的运维决策，不在本地开发中执行：重新核对活动执行、待续任务、调度/队列、浏览器会话、独立 worker、支付回调及外部请求；给出允许停机的精确对象和可能中断项，再取得对应授权。不能证明已有执行结束时，不把用户接受“停机”解释为同意取消、强杀或重跑任务。

允许中断的首次维护如另获授权，仍须保留并核对原任务与外部副作用，不能称为本设计的“无损排空通过”。结果不明时保持维护，禁止自动重放。若用户不接受中断风险，首次切换保持阻塞，不能为消除阻塞而改写数据。这是明确停止条件，不是一个待自动绕过的错误。

## 6. 发布顺序与失败恢复

1. **准备**：锁定候选 SHA、schema 差异、配置差异和精确进程身份。离线构建及隔离数据库演练提前完成；不在仍运行的 checkout 中先 reset/install/build。对有变更的服务逐一列出维护覆盖，未覆盖服务不自行停用。
2. **关闭接单**：保存维护标记，取得运行实例的维护确认；挡新执行并停止未来调度，保留原执行回执。旧版不支持时按第 5 节停止。
3. **等待与停止**：核对已跟踪任务、队列、后台工作和不明结果。确认可停后才停止指定进程，验证进程、监听端口、独立 worker/本次所属浏览器执行均已结束。超时不升级为强杀。
4. **升级**：维护保持有效，核对备份与恢复安排后执行明确批准的迁移。0059/0060 的范围与通用 runner 重放旧 SQL 的范围必须一致，不用“只有两个迁移”的说明运行全部旧 SQL。schema 校验失败保持维护。
5. **封闭验收**：候选以关闭状态启动，不运行自动恢复、计划派发或真实任务。验证构建身份、schema、静态页面、只读接口、维护拒绝行为和已有数据读取。会写数据的浏览器端到端用例在隔离 QA 中验收，不利用普通 localhost 或测试账号绕过生产维护。
6. **恢复接单**：同一候选实例检查通过且恢复服务获准后才开放准入和调度，最后恢复公网业务入口。启动恢复使用已验证的既有规则；身份不符或结果不明的任务不能自动续跑。任一步骤失败，立即保持/恢复关闭新准入，并等待已经接纳的工作，不宣布发布成功。

失败策略固定为：**迁移开始或候选首次启动之后，禁止现有 `abort_with_rollback` 自动把旧 checkout 启动对外服务。** 即使暂未观察到新格式记录，也不据此推断“从未写过新数据”。

恢复优先采用同数据格式的修复候选，在维护中重新校验。此设计不声称已存在一个验收合格的备用恢复 SHA。迁移前撤销发布，也仅能恢复经重新确认的原运行状态；原任务结果不明时同样不自动恢复接单。

不删新列、不将 NULL 费用改零、不重写执行身份、不重置用户额度、不批量将任务改为终态、不恢复整库覆盖维护期间的其他业务写入。恢复完成必须由实际数据读取、任务归属和接单行为验证，不能仅看 `/healthz`。

## 7. 实现边界与验收

拟触及：普通模式维护协调模块及本机控制入口；`application-main.ts` 启停；HTTP/tRPC、WS 与分离执行生命周期的接点；现有轮询/队列停止接点；部署与运行脚本及其测试。复用已有业务执行器、鉴权和幂等规则，不重写它们。原生 `ApplicationBoot` 路径及它的许可校验不纳入本项开放。

验收按一项整体交付，至少包含：

| 场景 | 必须观察到的结果 |
| --- | --- |
| HTTP/内部 caller 与维护并发 | 新请求不能新建任务、扣额度或派发外部调用；已接受任务的后续工作仍有归属 |
| 已有 WS 新指令与旧回执同时到达 | 新指令拒绝，匹配旧执行的回执可结算，无死锁 |
| 轮询停止后仍有分离子任务 | 不提前报告 idle；子任务实际结束后才允许停机 |
| 待用户确认、暂停和持久队列 | 数据保留；不靠清空状态满足排空 |
| 扩展断线、远端请求超时、清理失败 | 结果不明或停机不明；无自动强杀、重跑、恢复接单 |
| 新进程启动时维护标记存在 | HTTP/WS 不接新执行，定时与恢复不派发；重启不绕过 |
| 迁移/启动/封闭验收失败 | 仍关闭；假 SSH/假 PM2 证明未调用旧版自动启动 |
| 已有新执行记录、NULL 费用 | 兼容候选正确读取；旧版恢复路径拒绝，记录未被改写 |
| 旧版本无维护协议 | 变更前退出，明确首次引导所需决策，无“视作通过”分支 |
| 正常维护与恢复 | 同实例状态顺序正确，恢复只发生一次，无重复派发或扣费 |

测试先用假时钟、可控制的任务 Promise、真实本地 HTTP/WS、独立子进程和假部署命令，外部服务不使用真实凭据。数据库用独立合成库；浏览器后续仅使用已批准的 QA 范围。权限拒绝、未运行、模拟测试、隔离真服务测试、生产验证分别记录。既往全量测试不是本项的新证据。
