# HOLA DAY 自助账号关闭编排器设计

日期：2026-08-26

状态：产品与架构设计已确认，待书面规格复核

类型：架构级

基线：`74ab34c6`（PR #148 合并结果）

## 1. 背景

HOLA DAY 当前的账号删除入口仍以人工邮件申请为主。机器可读数据治理注册表已经覆盖 13 个稳定数据类别，但账号关闭能力仍登记为人工处理，尚不存在能够跨账号、任务、文件、对象存储、股票画像、通知、支付和治理记录可靠运行的自动编排器。

账号关闭不能简化为一条 `DELETE users`：大量业务表依赖用户主键并可能发生级联删除，而支付、退款、争议、安全审计、合伙人 KYC 与账本等记录又可能需要按业务或适用法律受限保留；文件还同时存在数据库元数据和对象存储实体。若缺少持久化步骤、幂等重试和精确恢复，任何中途故障都可能造成数据残留、账务误删或账号错误恢复。

本设计建设首版自助账号关闭能力。用户提交申请后立即失去正常访问，获得 7 天冷静期；冷静期结束后，系统按治理类别逐项删除、不可逆匿名化或受限保留数据，最终生成不包含原始个人内容的关闭回执。

## 2. 已确认的产品决策

1. 使用 7×24 小时冷静期。申请后立即停用账号并撤销会话，到期后异步清理。
2. 冷静期内，用户登录只进入专用恢复页。撤回必须再次验证已绑定邮箱或手机号；启用 MFA 时还需通过 MFA。密码本身不能自动恢复账号。
3. 有效套餐不阻止关闭，但关闭不自动退款。套餐和额度在最终关闭时失效；冷静期内撤回后继续使用原到期时间和原额度，不补偿冷静期天数。
4. 申请后立即禁止新任务，取消运行中任务，暂停规划任务、定时任务、股票监控和外部通知。
5. 最终关闭后，原邮箱或手机号可以注册全新账号；新账号不继承任何旧任务、文件、套餐、额度、偏好或历史。
6. 第一版只建设账号关闭和关闭回执，不同时建设完整个人数据导出系统。
7. 采用数据库持久化、可重试的关闭编排器，不使用单次事务硬删除或纯人工清理。

## 3. 目标

首版必须做到：

1. 提供用户可理解、可验证、无暗黑模式的自助关闭入口；
2. 申请后立即阻断所有正常访问和新增执行；
3. 在 7 天冷静期内提供强验证撤回，并精确恢复本次流程暂停的资源；
4. 通过持久化步骤逐类处理 13 个治理数据类别；
5. 保证数据库、对象存储和外部通知故障下可安全重试；
6. 删除不再需要的个人数据，同时保护依法或业务必要的账务、安全和争议记录；
7. 释放原邮箱和手机号，允许创建完全独立的新账号；
8. 让治理注册表、隐私公开说明和真实处理器保持一致；
9. 在 16GB 主机上以单并发、约 512MB 工作进程预算运行，使整机长期内存目标保持在约 10GB 内；
10. 生成不包含任务正文、文件名、偏好、邮箱或手机号的关闭回执。

## 4. 非目标

首版不包含：

- 完整个人数据导出、自助数据携带或跨平台迁移；
- 自动退款、套餐按天折算或支付架构重构；
- 账号合并、旧账号数据恢复或新旧账号关联；
- 自动推断具体法定保存年限；
- 自动解除法律保留、争议保留或安全调查保留；
- 从其他设备、浏览器扩展或用户已下载介质中远程删除副本；
- 用真实用户账号执行破坏性上线验证；
- 顺带重构与账号关闭无关的任务、支付、股票或媒体系统。

## 5. 核心原则

### 5.1 先冻结，后清理

账号访问和任务准入在申请成功时立即停止。数据永久清理只能在冷静期结束并由执行器原子取得申请后开始。

### 5.2 显式处理优于数据库级联

每个治理数据类别必须有明确处理器和完成证据。不得把删除用户行产生的级联效果当作完整关闭实现。

### 5.3 失败关闭而非失败开放

任何清理失败都不能恢复账号访问、重启任务或发出虚假完成回执。失败申请保持关闭状态，进入重试或人工关注。

### 5.4 最小化保留

需要保留的记录必须去除非必要身份字段，并进入受限用途和受限访问边界。不能以“审计”为由保留全部用户内容。

### 5.5 稳定治理 ID

执行步骤使用数据治理注册表中的稳定类别 ID。新增数据类别时，缺少关闭处理器必须使治理检查和发布检查失败。

### 5.6 不依赖单机内存状态

截止时间、执行权、步骤状态、重试、检查点和回执全部持久化。服务重启不能丢失关闭申请或重复产生不可控副作用。

## 6. 系统边界与组件

首版由五个清晰单元组成：

1. **账号关闭 API**：预览影响、发送验证、创建申请、查询状态和撤回申请；
2. **访问门禁**：统一阻断关闭中账号的会话、登录、刷新令牌、API Key 和业务写入；
3. **即时停止服务**：取消运行任务，并暂停未来任务、股票监控和通知；
4. **关闭执行器**：在截止时间后按类别串行清理、匿名化或受限保留；
5. **回执与治理适配层**：生成回执，更新治理能力状态，并提供聚合运行指标。

关闭执行器使用 Orchestrator 同一代码库和数据库，但以独立、受资源限制的工作进程运行。它不是新的公网服务，也不暴露独立用户接口。

## 7. 状态模型

### 7.1 用户状态

用户账号状态至少包含：

- `active`：正常使用；
- `closure_pending`：冷静期内，仅允许进入恢复流程；
- `closure_processing`：到期后正在清理，不允许自助撤回；
- `closed`：最小化封存主体，不可登录。

最终状态采用最小化封存用户主体，而不是直接删除用户主键。封存时移除或替换邮箱、手机号、密码、OAuth 绑定、MFA、昵称、头像等身份和认证字段，保留一个不可登录的内部主体以承接受限账务或审计引用，并释放原邮箱和手机号唯一键。

### 7.2 关闭申请状态

```text
pending_grace
  ├─ cancelled
  └─ processing
       ├─ completed
       └─ needs_attention
```

- `pending_grace`：7 天冷静期；
- `cancelled`：用户在截止前完成验证并撤回；
- `processing`：执行器已原子取得申请；
- `needs_attention`：存在超过自动重试阈值或配置缺口的步骤；
- `completed`：所有必需步骤成功，回执生成，身份键释放。

`needs_attention` 不是终态。问题修复后仍从原步骤继续，最终进入 `completed`。

### 7.3 步骤状态

每个数据类别步骤使用：

- `pending`；
- `running`；
- `succeeded`；
- `retryable`；
- `blocked`；
- `skipped`。

`skipped` 只允许表示该用户确实不存在该类别数据，不能表示处理器尚未实现。

## 8. 申请、冻结和撤回

### 8.1 申请前预览

设置页调用只读预览接口，返回当前套餐到期时间以及将被暂停、取消或删除的资源聚合数量。预览不返回任务正文、文件名或内部数据主键。

### 8.2 申请验证

申请要求近期有效会话和再次验证：

- 邮箱账号使用账号关闭专用邮箱验证码；
- 仅手机号账号使用账号关闭专用短信验证码；
- 开启 MFA 的账号在上述验证后额外完成 MFA。

验证码用途必须与登录、密码修改和撤回用途隔离，短时有效、一次性消费并限流。

### 8.3 原子冻结

申请确认时，在数据库事务中：

1. 校验用户仍为 `active` 且不存在未结束申请；
2. 创建 `account_closure_requests`；
3. 将用户改为 `closure_pending`；
4. `authVersion + 1`；
5. 撤销数据库会话、Refresh Token 和 API Key；
6. 建立即时停止步骤和资源影响记录；
7. 写入不含原始个人内容的安全审计事件。

用户状态是业务准入的最终门禁。即使后续取消外部任务暂时失败，也不能继续创建新任务或访问正常产品。

### 8.4 即时停止范围

- 禁止所有新任务；
- 请求取消正在运行的普通、批量和浏览器任务；
- 暂停未来的规划任务和定时任务；
- 暂停股票监控和由此产生的外部通知；
- 禁用用户配置的 webhook、企业微信、飞书、钉钉等通知发送；
- 保留每项资源在关闭前的状态，并只记录由本次关闭流程实际改变的资源。

外部取消失败进入持久化重试。它不回滚账号冻结。

### 8.5 撤回竞争控制

撤回只允许同时满足：

1. 当前时间早于服务端 `graceEndsAt`；
2. 申请仍为 `pending_grace`；
3. 执行器尚未取得处理权；
4. 用户重新通过邮箱或短信验证，且按需通过 MFA。

撤回和执行器使用条件更新或行锁竞争同一申请，二者只能有一个成功。撤回成功后：

- 用户恢复为 `active`；
- 再次递增 `authVersion`；
- 只恢复 `account_closure_effects` 中由本次流程暂停的资源；
- 已取消的运行中任务不自动重跑；
- 原套餐到期时间和额度保持不变，不延长冷静期占用的时间；
- 所有关闭恢复凭证立即失效。

## 9. 数据模型

### 9.1 `account_closure_requests`

概念字段包括：

- `id`、`userId`；
- `status`；
- `requestedAt`、`graceEndsAt`；
- `processingStartedAt`、`completedAt`、`cancelledAt`；
- `receiptNumber`；
- 可选固定枚举 `reasonCode`；
- `createdAt`、`updatedAt`。

禁止保存自由文本关闭原因。数据库使用部分唯一索引或等价约束，保证同一用户最多存在一条未结束申请。

### 9.2 `account_closure_steps`

概念字段包括：

- `requestId`、`categoryId`、`handlerVersion`；
- `status`、`attemptCount`、`nextAttemptAt`；
- `leaseOwner`、`leaseUntil`；
- 不含个人内容的分页 `checkpoint`；
- 枚举化 `lastErrorCode`；
- `startedAt`、`finishedAt`、`updatedAt`。

`requestId + categoryId` 唯一。检查点只能保存游标和聚合计数，不能保存任务正文、文件名、邮箱、手机号或其他个人内容。

### 9.3 `account_closure_effects`

该表只保存恢复所需的最小引用：

- `requestId`；
- `resourceType`；
- `resourceId`；
- `previousState`；
- `closureAppliedState`；
- `restoredAt`。

撤回或最终关闭完成后，按对应状态清理该临时记录。恢复必须再次核对资源属于同一用户，防止越权。

### 9.4 `account_closure_receipts`

回执保存：

- 随机且不可枚举的回执编号；
- 申请、到期、完成时间；
- 已完成的数据类别；
- 受限保留的数据类别；
- 关闭结果；
- 不可逆关闭主体摘要。

回执不得保存邮箱、手机号、任务正文、文件名、股票偏好、验证码、令牌或自由文本。完成后，它不依赖可登录用户主体。

## 10. 登录与访问门禁

以下全部入口必须先检查用户状态：

- 密码登录；
- 邮箱验证码登录；
- 手机短信登录；
- Google/OAuth 登录；
- MFA 后续登录；
- Refresh Token；
- API Key；
- 现有会话续期；
- WebSocket 或长连接重新认证。

`closure_pending` 用户不能获得普通访问令牌，只能获得短期、受用途限制的恢复凭证。恢复凭证仅允许：

- 查询关闭状态；
- 请求撤回验证码；
- 提交撤回；
- 查看或下载申请回执；
- 退出恢复流程。

`closure_processing` 和 `closed` 均不能签发正常令牌。用户 ID 只能从已验证会话或恢复凭证中取得，账号关闭 API 不接受客户端传入 `userId`。

## 11. 13 类治理数据的处理规则

| 治理类别 | 最终处理 |
|---|---|
| `account_security` | 撤销会话、Refresh Token、API Key；删除 MFA、OAuth 绑定和认证信息；把用户主体最小化封存并释放邮箱、手机号 |
| `task_execution` | 删除任务、步骤、结果、截图、浏览器上下文、关联文件和对象存储实体；依法保留的安全证据另行受限处理 |
| `cross_task_memory` | 删除账号范围记忆、摘要、偏好和关联索引 |
| `energy_astrology_profile` | 删除服务器端关联资料；当前设备清理本地资料；其他设备提供明确自行清理说明 |
| `stock_preference_profile` | 删除主动偏好、筛选依据、自选股、观察、监控、快照和关联通知配置 |
| `feedback_support` | 删除普通反馈与账号关联；仍在处理的争议或法律保留材料进入受限记录并最小化身份字段 |
| `external_notifications` | 删除 webhook 和外部渠道配置、模板、发送队列及可删除历史 |
| `extension_site_stats` | 删除服务器端域名聚合；说明服务器无法远程清除其他设备扩展本地副本 |
| `extension_login_cookies` | 删除待注入 Cookie、加密封装、兼容字段和关联队列；撤销服务端注入资格 |
| `payments_entitlements` | 删除套餐权益、额度和非必要付款资料；订单、退款、争议及必要结算记录去标识后受限保留 |
| `partner_kyc_ledger` | 删除非必要展示资料；按已审定策略受限保留必要 KYC、账本、提现、风控、税务或争议记录 |
| `media_assets` | 删除图片、视频、语音、声音克隆素材及对象；必要的授权或争议证明最小化后受限保留 |
| `analytics_logs` | 删除或不可逆匿名化可识别事件和访客关联；仅保留无法重新识别个人的聚合指标及必要安全审计 |

新增第 14 类数据时，必须先增加稳定治理 ID、关闭处理器、保留规则、测试和公开披露复核，才能发布相关业务功能。

## 12. 文件、对象存储和外部系统

文件清理采用两阶段语义：

1. 标记文件记录进入关闭清理；
2. 删除 R2 或其他对象存储实体；
3. 确认对象不存在后删除数据库元数据；
4. 保存分页检查点并继续下一批。

对象本来不存在视为幂等成功。对象删除超时或失败时，数据库保留待清理状态并重试，不能提前声称完成。

对于外部通知、模型供应商或抓取服务，首版不承诺远程删除第三方已依法独立保存的记录。关闭处理器必须停止后续发送、清除 HOLA DAY 保存的凭据和队列，并按已核实的处理方能力执行可用删除请求；无法自动完成的边界必须在治理登记和公开说明中如实保留。

## 13. 支付、账务与身份复用

最终关闭前，执行器必须先处理支付和合伙人账务引用，不能依赖 `ON DELETE CASCADE`。

受限保留记录：

- 移除邮箱、手机号、昵称等非必要字段；
- 关联到不可登录的封存主体或专用受限主体键；
- 仅允许支付、对账、争议、安全或依法要求的角色访问；
- 不参与产品推荐、画像、营销或新账号恢复；
- 保留期限来自单独的已审核策略，不在本功能中猜测固定年限。

封存用户主体使用不可路由的随机占位身份，原邮箱和手机号解除唯一约束占用。用户可用原身份注册新账号，新账号获得新用户 ID，系统不得自动关联、恢复或迁移旧数据。

为安全、争议和反滥用保留的身份摘要必须使用服务端专用密钥计算，并与普通产品查询隔离。摘要不能替代原始身份在产品侧展示，也不能用于恢复旧账号。

## 14. 关闭执行器

### 14.1 运行方式

执行器是独立、无公网入口的 Orchestrator 工作进程：

- 初始全局并发固定为 1；
- 一次领取一个申请；
- 一个申请内一次处理一个数据类别；
- 使用数据库租约和心跳；
- 租约到期后其他实例可重新领取；
- 不使用仅存在于进程内的长期定时器作为事实来源。

### 14.2 到期抢占

执行器只领取 `graceEndsAt <= now()` 且状态为 `pending_grace` 的申请，通过条件更新或行锁原子转为 `processing`。撤回与领取不能同时成功。

领取成功时，用户状态在同一事务中从 `closure_pending` 变为 `closure_processing`。申请进入 `needs_attention` 时，用户仍保持 `closure_processing`；只有全部完成条件满足后，用户才变为 `closed`。

7 天以服务端 UTC 保存为精确的 7×24 小时。界面根据用户时区显示，但显示时区不能改变服务端截止时间。

### 14.3 幂等与检查点

每个处理器以 `requestId + categoryId` 为幂等键，并满足：

- 删除不存在对象视为成功；
- 重复执行不影响其他用户；
- 分页处理后保存游标和计数；
- 进程崩溃后从最后安全检查点继续；
- 只有整类数据完成后才标记 `succeeded`；
- 缺少处理器时标记 `blocked`，不能使用 `skipped` 代替。

### 14.4 重试

数据库瞬时故障、对象存储超时和外部通知失败使用有上限的指数退避。超过自动重试阈值后：

- 申请进入 `needs_attention`；
- 发送不含个人内容的内部告警；
- 只进行低频安全重试；
- 不恢复账号访问；
- 不生成完成回执。

修复处理器或基础设施后，从失败步骤继续，无需用户重新申请。

### 14.5 资源预算

- 工作进程并发固定为 1；
- 数据库使用有界游标分页；
- 对象存储采用小批次和有限连接；
- 不下载文件内容进行删除；
- 禁止无界数组、全表读取和无界 Promise 并发；
- 工作进程 RSS 预算约 512MB；
- 接近预算时停止领取新任务，在保存安全检查点后退出并告警；
- 部署资源规划以整机长期占用约 10GB 为目标，为 16GB 主机保留数据库、部署和突发流量余量。

## 15. 完成条件与回执

申请只有同时满足以下条件才能进入 `completed`：

1. 所有应删除类别为 `succeeded`；
2. 对象存储不存在遗留待删除对象；
3. 受限记录已完成去标识和权限隔离；
4. 原邮箱和手机号已释放；
5. 登录、API Key、任务和通知不可恢复执行；
6. 套餐权益和额度已失效；
7. 不存在 `pending`、`running`、`retryable` 或 `blocked` 步骤；
8. 完成回执已经生成，最小完成通知已被通信服务接受。

回执分为申请回执和完成回执。两者只包含回执编号、状态时间、处理类别和受限保留类别，不包含任何原始个人内容。系统不提供公开回执查询；用户可凭回执编号联系人工支持。

最终身份清除按固定顺序执行：先生成完成回执，再通过仍有效的验证邮箱或手机号提交最小完成通知，通信服务确认接受后立即清除或替换真实联系方式并释放唯一键。通知发送失败进入有界重试，在成功前不得声明 `completed`；该阶段仍禁止正常登录和产品访问。

## 16. 用户体验

### 16.1 设置页

“设置 → 账号与安全”底部提供独立关闭入口，动态展示：

- 7 天冷静期和预计最终日期；
- 当前套餐和到期时间；
- 将暂停、取消或删除的资源聚合数量；
- 依法或业务必要受限保留的类别；
- 关闭不会自动退款。

### 16.2 三步确认

1. 阅读影响：立即退出、任务停止、7 天可撤回、到期不可恢复；
2. 确认三项关键后果，不要求输入长句；
3. 完成邮箱或短信验证，并按需完成 MFA。

关闭原因只允许可选固定枚举，不收集自由文本，也不能阻止提交。

### 16.3 恢复页

`closure_pending` 用户登录后只能进入 `/account/closure-recovery`。页面显示精确截止时间、暂停能力、删除/保留概要、申请回执编号和撤回入口。用户不能访问首页、任务、文件、股票、计划或其他正常功能。

到期进入处理后，页面只显示“正在完成账号关闭”、回执编号和人工支持渠道，不再显示自助撤回按钮，也不暴露内部错误。

### 16.4 本地副本说明

提交申请时立即清除当前设备的正常登录态，并在申请回执页提供“立即清除本机资料”入口。冷静期结束后，如果用户仍打开或重新进入恢复页，前端再次尽力清除当前浏览器的可识别缓存。页面明确说明服务器无法远程清除其他设备浏览器扩展、本地缓存或用户已下载文件，并提供简短自行清理指引。

本地副本无法由服务器证明已删除，因此不作为服务端 `completed` 的完成条件，也不得在回执中声称所有设备副本已经销毁。

## 17. API 设计

概念接口如下，最终命名遵循现有 Orchestrator 路由约定：

- `accountClosure.preview`：读取影响聚合；
- `accountClosure.requestVerification`：发送申请专用验证码；
- `accountClosure.begin`：消费验证并创建申请；
- `accountClosure.status`：使用恢复凭证读取状态；
- `accountClosure.requestCancellationVerification`：发送撤回专用验证码；
- `accountClosure.cancel`：消费验证并撤回；
- `accountClosure.applicationReceipt`：读取或下载申请回执。

所有写接口必须限流、一次性消费挑战、验证请求来源并产生不含个人内容的审计事件。错误响应防止账号枚举，不向未验证请求确认某个邮箱或手机号是否存在或处于关闭中。

## 18. 可观测性与隐私

允许记录：

- 关闭申请内部编号；
- 治理类别 ID；
- 步骤状态、尝试次数、耗时和枚举错误码；
- 待处理、成功和失败聚合数量；
- 租约、队列长度和工作进程内存。

禁止记录：

- 邮箱、手机号、姓名和地址；
- 任务正文、文件名、股票偏好和反馈文本；
- Cookie、验证码、令牌、API Key 或对象内容；
- 可逆身份映射。

生产监控至少包含：队列长度、最老申请年龄、完成率、重试率、`needs_attention` 数量、各类别耗时、对象存储遗留数和执行器 RSS。

## 19. 测试策略

### 19.1 单元与契约测试

- 状态机只允许合法转换；
- 7×24 小时计算与时区显示正确；
- 验证码 purpose 隔离、过期、重放和限流；
- 每个治理类别存在处理器；
- 新类别缺少处理器时治理审计失败；
- 日志字段契约拒绝个人内容；
- 回执不包含禁止字段。

### 19.2 集成测试

- 关闭申请和重复提交；
- 撤回与执行器到期领取竞争；
- 所有登录、刷新、API Key 和长连接入口被阻断；
- 只恢复本次关闭暂停的资源；
- 已取消运行任务不自动重跑；
- 对象存储失败、数据库重启、租约超时和工作进程崩溃后的续跑；
- 重复执行步骤不误删或重复产生副作用；
- 支付、退款、争议和合伙人账务记录不被级联误删；
- 原邮箱和手机号重新注册后获得新用户 ID，且无法访问旧数据；
- 套餐在撤回时保持原到期时间，在最终关闭时失效；
- 处理失败时不发送完成回执。

### 19.3 前端与可访问性测试

- 桌面和移动端三步关闭流程；
- 冷静期倒计时和精确时间；
- 恢复页不能进入正常产品；
- 键盘操作、焦点管理、读屏标签和错误反馈；
- 重复点击和网络重试不重复创建申请；
- 申请、处理和完成状态文案与真实后端状态一致。

### 19.4 资源与隐私测试

- 使用合成大数据测试账号验证有界分页和检查点；
- 执行器单并发且 RSS 保持在约 512MB 预算内；
- 扫描日志、错误追踪和回执，确认没有个人原文；
- 验证整机压力下执行器停止领取新任务而不破坏已有步骤；
- 不使用真实用户账号进行破坏性测试。

## 20. 灰度发布与回退

按以下顺序发布：

1. 扩展数据库结构，关闭入口和执行器保持禁用；
2. 上线 API、门禁和工作进程代码，功能开关仍关闭；
3. 仅允许专用内部测试账号申请；
4. 覆盖申请、撤回、到期、故障重试、受限保留和重新注册；
5. 核对对象存储、支付账务、治理登记、日志隐私和内存指标；
6. 先开放员工账号，再逐步开放全部用户；
7. 持续观察队列、延迟、完成、失败和资源指标。

发生异常时：

- 关闭新申请入口；
- 停止执行器领取新步骤；
- 保留已有申请、租约和检查点；
- 不回滚已经完成的不可逆清理；
- 修复后从安全检查点继续；
- 数据库迁移只采用向前兼容的扩展式发布，在所有处理中申请结束前不删除结构。

## 21. 上线验收标准

只有以下全部通过，才能开放给全部用户：

1. 申请后所有正常访问和新任务立即失效；
2. 运行任务取消、未来任务和通知暂停可靠；
3. 7 天内撤回安全且恢复范围精确；
4. 到期处理可从故障中恢复，无孤儿文件；
5. 支付、账务、争议、安全和必要授权记录不被误删，也不过度保留；
6. 原身份可以重新注册，旧数据不可恢复或自动关联；
7. 回执准确且不含个人原文；
8. 全部认证入口、并发竞争和幂等测试通过；
9. 治理注册表、隐私公开说明和真实处理器一致；
10. 执行器满足单并发和约 512MB 内存预算；
11. 生产监控、告警和人工异常处理路径可用；
12. 完整个人数据导出仍明确标记为未实现或人工处理，不因账号关闭上线而被错误声明为已实现。

## 22. 实施边界

本设计可以作为一个实施计划，但计划应按依赖顺序拆成可独立验证的阶段：

1. schema、状态机和治理处理器契约；
2. 申请验证、冻结、登录门禁和恢复凭证；
3. 即时任务/通知停止与精确撤回；
4. 13 类数据处理器、文件/R2 清理和受限保留；
5. 执行器、重试、回执和可观测性；
6. 设置页、恢复页、契约测试和灰度发布。

实施计划不得把“账号关闭”扩张为数据导出、自动退款或支付系统重构。任何实际保留期限和法律例外仍需绑定已审定的保留策略，工程实现不代替法律意见。
