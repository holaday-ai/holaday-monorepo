### Task 1 · executing 重启重发 dispatch（W1 backlog b1）

设计文档 §Milestone 1 "Agent Loop 崩溃恢复"之前只覆盖了 `awaiting_user` 和 `paused`，`executing` 任务在重启后会静默卡死。现在：

```
executing → 重启 → rehydrateInFlight 读出 cursor 步
         → WS 重连 → applyRehydrationForUser
         → send server.task.dispatch(plan[cursor])
         → 扩展恢复执行
```

实现细节：
- `applyRehydrationForUser` 现在按 status 分派：`awaiting_user`/`paused`/`executing` 各自重发对应帧。
- `planning`/`pending` 记 warn 跳过（理论上不该持久化到这个状态；真到了这儿 commander 需要 re-plan，Phase 0 外延）。
- 新日志字段 `reemitted: {dispatch, confirm, pause}` 计数，ops 侧直接能看到重启恢复了哪些状态。
- `cursor` 越界也是 warn + skip，不 crash 重连。

集成测试：`ws/restart-recovery-executing.integration.test.ts` — seed 一个 cursor=1 的 executing task → fresh `loadRehydratedTasks` + fresh WS server → 新客户端连入 → 5 秒内收到 `server.task.dispatch` stepId 正确。

## 明日（W2 Day 2）计划

`douyin-comment-manager` Skill：抖音商家后台评论管理。

### 场景考虑

- **典型意图**："帮我看看今天有哪些差评没回"、"把 5 分好评批量置顶"、"昨晚直播间评论里带手机号的帮我标出来"。
- **与 compass-export 的区别**：这次是**写场景**。回评、置顶、删除、屏蔽都是高危动作，必须走 `awaiting_user` 确认流程。
- **riskFloor 设计**：基础 `low`（浏览、extract 评论列表），但执行写动作的具体 step 标 `risk: 'high'` + `requiresConfirm: true`。批量写（例如"一次性回 10 条"）强制逐条确认。
- **合规**：不代写带承诺的话术（"包邮"、"免责"、"退款"），只帮用户 draft 一个基础回复让用户自己按 Confirm 之前检查。

### 技术上需要处理的新点

1. **批量操作的多次 awaiting_user**：当前 `awaiting_user` 触发在 onStepResult 里，每次一步。批量要么展开成 N 个 step（commander 规划时做），要么扩展 `pendingConfirm` 支持"N 个子项"。Day 2 先按"每个写动作一步"展开，不做批量 schema。
2. **"preview draft, then confirm"**：有些 Skill 想让 commander 先生成回复草稿（LLM 一次额外调用），再由用户 Confirm。这是 Day 2 的次决策——倾向"Skill 里展开成 2 个 step（draft + send），send 是 high-risk"。
3. **抖音商家后台的站点范围**：compass 是 jinritemai.com；评论管理可能在 `live.jinritemai.com/live_center/` 或商家工作台的新 URL。Day 2 先写 SKILL.md 时确定 entryUrls。

## 风险 / 需要决策
